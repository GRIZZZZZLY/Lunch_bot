# Справочник магазинов и личные пресеты товаров

Дата: 2026-09-03. Статус: утверждён к реализации.

## Задача

Две связанные вещи в сценарии «поход в магазин» (`StoreRun`):

1. **«Откуда заказываем»** — магазины перестают быть свободным текстом в каждом
   забеге и накапливаются в справочнике группы.
2. **Свои сохранённые товары** — у каждого пользователя копится личный список
   позиций, которые он добавляет в забеги.

Сегодня `StoreRun.storeName` — строка до 100 символов, вводимая заново каждый
раз; `StoreItem` создаётся из пустой формы. Ни истории, ни подсказок.

## Решения (утверждены владельцем)

| Вопрос | Решение |
|---|---|
| Чей справочник магазинов | Группы |
| Кто правит и удаляет магазины | Любой активный участник группы |
| Поля магазина | Только название |
| Как копятся пресеты товаров | Автоматически при добавлении, плюс закрепление |
| Привязка пресетов к магазину | Общие, но сортировка учитывает текущий магазин |
| Поля пресета | Название + количество + заметка |
| Как добавлять пресеты в забег | Список с мультивыбором, один bulk-запрос |
| Бэкфилл из истории | Нет, с нуля |
| Дедупликация | Обязательна, без учёта регистра |
| Удаление магазина | Soft delete, история цела |
| Переименование магазина | Активные забеги обновить, завершённые не трогать |
| Правка позиции в забеге | Обновляет пресет (пресет = последнее состояние) |
| Где управлять пресетами | В той же шторке «Мои товары» |

## Модель данных

### `GroupStore` (`group_stores`)

| Поле | Тип | Смысл |
|---|---|---|
| `id` | Int PK | |
| `groupId` | Int FK → Group, cascade | владелец справочника |
| `name` | String ≤100 | как ввёл пользователь |
| `normalizedName` | String | ключ дедупликации |
| `createdById` | Int FK → User | кто завёл |
| `lastUsedAt` | DateTime | сортировка чипов |
| `usageCount` | Int | вторичный сигнал |
| `archivedAt` | DateTime? | soft delete |

`@@unique([groupId, normalizedName])` — дедупликация на уровне БД, а не только
в сервисе: два одновременных запроса с одинаковым именем иначе создадут дубль.
`@@index([groupId, archivedAt, lastUsedAt])` — под запрос списка.

### `UserItemPreset` (`user_item_presets`)

| Поле | Тип | Смысл |
|---|---|---|
| `id` | Int PK | |
| `userId` | Int FK → User, cascade | владелец |
| `name` | String ≤200 | |
| `normalizedName` | String | ключ дедупликации |
| `quantity` | Int 1..99 | последнее использованное |
| `notes` | String? ≤500 | последняя заметка |
| `pinned` | Boolean | закреплённые всегда сверху |
| `usageCount` | Int | |
| `lastUsedAt` | DateTime | |

`@@unique([userId, normalizedName])`, `@@index([userId, pinned, lastUsedAt])`.

### `StoreRun`

Добавляется `storeId Int?` → `GroupStore`, `onDelete: SetNull`. Поле
`storeName` **остаётся**: это снимок имени на момент забега, он держит историю
и старые записи без `storeId`. Добавляется `@@index([storeId])` — под подсчёт
«брал ли пользователь этот товар в этом магазине».

### Нормализация

Одна функция `normalizeName` в `backend/src/utils/normalize-name.ts`:
trim → lower → `ё` → `е` → схлопывание внутренних пробелов. Общая для обеих
таблиц, покрыта unit-тестами. Уникальный индекс ловит гонку, сервис ловит
`P2002` и делает повторный `findUnique`.

## Бэкенд

### Магазины: `/api/groups/:groupId/stores`

| Метод | Поведение |
|---|---|
| `GET /` | активные магазины группы, `lastUsedAt desc`, лимит 30 |
| `PATCH /:id` | переименование; конфликт с другим активным → `409 STORE_EXISTS`; обновляет `storeName` у забегов этой группы в `COLLECTING`/`SHOPPING` с этим `storeId` |
| `DELETE /:id` | `archivedAt = now()` |

Отдельного `POST` нет — запись рождается в `createStoreRun`. Права: активный
`GroupMember`. Ошибки — свой `GroupStoreError` с кодами `NOT_FOUND`,
`FORBIDDEN`, `INVALID_INPUT`, `STORE_EXISTS`.

Переименование в имя архивированной записи запрещено (`409`), а не сливает две
строки: слияние переписало бы `storeId` у чужих завершённых забегов. Чтобы
вернуть архивированный магазин, достаточно снова ввести его имя при создании
забега — это его «воскрешает».

### `createStoreRun`

Тело получает необязательный `storeId`. Логика:

- `storeId` задан → проверить принадлежность группе и `archivedAt == null`,
  имя берётся из справочника;
- иначе `storeName` → upsert по `(groupId, normalizedName)`; найденная
  архивированная запись воскресает (`archivedAt = null`) и получает новое
  написание имени;
- в обоих случаях `usageCount++`, `lastUsedAt = now()`.

Найденная **активная** запись написание НЕ меняет: «пятерочка» не должна
переименовывать «Пятёрочку». Переименование — только явное, через `PATCH`.

Всё это внутри той же транзакции, что и создание забега, чтобы отменённое
создание не оставило магазин.

### Пресеты: `/api/user/item-presets`

| Метод | Поведение |
|---|---|
| `GET /?storeId=` | `pinned desc`, затем «брал в этом магазине» desc, затем `lastUsedAt desc`, лимит 50 |
| `PATCH /:id` | `pinned`, `name`, `quantity`, `notes` |
| `DELETE /:id` | физическое удаление — это личные данные |

Автозапись: `addItemsBulk` и `updateItem` после успешной записи вызывают
`UserItemPresetService.recordUsage`. Вызов **вне** транзакции позиции и в
`try/catch` с логом: сбой пресета не должен ронять добавление товара.
Вытеснение: если незакреплённых больше 50, удаляются самые старые по
`lastUsedAt`.

## Фронтенд

### `CreateStoreRunSheet`

Ряд чипов над полем ввода из `GET /groups/:groupId/stores` (до 8 видимых). Тап
заполняет поле и ставит `storeId`. Ручная правка текста сбрасывает `storeId` —
дальше сервер матчит по нормализованному имени. Долгое нажатие на чип →
шторка «Переименовать / Скрыть». Пустой справочник — форма как сегодня.

### `AddStoreItemSheet`

Две вкладки: «Мои товары» и «Новая». По умолчанию первая, если пресеты есть.
Список: чекбокс, название, количество и заметка, кнопка закрепления, кнопка
удаления. Нижняя кнопка «Добавить N» — один вызов `addItems`. Пресеты, уже
добавленные этим пользователем в текущий забег, помечены «уже в списке» и без
чекбокса.

Новые файлы: `features/store-run/components/StoreChips.tsx`,
`ItemPresetList.tsx`, `services/group-store.service.ts`,
`services/item-preset.service.ts`, хуки `useGroupStores`, `useItemPresets`.
Инвалидация: после `createRun` — магазины, после `addItems`/`updateItem` —
пресеты.

Визуальный слой — по правилам `CLAUDE.md`: существующие токены, состояния
`hover`/`focus-visible`/`active`, 44×44, светлая и тёмная темы, 390 px.

## Краевые случаи

- Пользователь вышел из группы: пресеты личные, не трогаем; магазины остаются
  в группе.
- Один пресет добавлен в забег дважды — обычный дубль позиции, как при ручном
  вводе. Защита только визуальная.
- Длина заметки пресета наследует валидацию позиции, отдельного пути ввода нет.
- Забеги без `storeId` (созданные до фичи) показывают `storeName` и работают
  как раньше.

## Тесты

- Unit: `normalizeName`; `GroupStoreService` — upsert, воскрешение,
  конфликт переименования, обновление только активных забегов;
  `UserItemPresetService` — upsert, вытеснение, сортировка по магазину,
  изоляция ошибок `recordUsage`.
- Контроллеры: не-член группы → 403, конфликт → 409, валидация тел;
  `api-surface.test.ts` дополняется новыми маршрутами.
- Фронт: `StoreChips` (выбор, сброс `storeId`), `ItemPresetList` (мультивыбор,
  закрепление, удаление, «уже в списке»), обновлённые тесты обеих шторок.
- E2E smoke: создание забега через чип, добавление двух пресетов одной кнопкой.
