# Конституция проекта Telegram Food Bot

## Основные принципы

### I. Архитектура сервисного слоя

Вся бизнес-логика ДОЛЖНА находиться в stateless сервисах в `backend/src/services/`. Контроллеры и обработчики бота являются тонкими фасадами, делегирующими работу сервисам. Каждый сервис имеет единственную, чётко определённую доменную ответственность (опросы, голоса, меню, пользователи, уведомления, рулетка).

**Обоснование**: Обеспечивает тестируемость бизнес-логики, её переиспользование и независимость от транспортного слоя (бот vs. API). Предотвращает дублирование между командами Telegram бота и REST API endpoints.

### II. Гибридная модель коммуникации

Бот ДОЛЖЕН минимизировать спам в групповом чате через гибридный поток: Групповой чат → Deep Link → Личный чат → Mini App. Сообщения в группе ограничены 3 на жизненный цикл опроса (создание, напоминание, результаты). Голосование и детальные взаимодействия происходят в личном чате или Mini App.

**Обоснование**: Telegram группы — общее пространство. Избыточные сообщения бота создают шум и приводят к удалению бота. Паттерн deep linking уважает группу, предоставляя богатое взаимодействие в подходящих контекстах.

### III. 100% обратная совместимость

Каждая функция Mini App ДОЛЖНА иметь чистый Telegram-фолбэк через inline клавиатуры и callback queries. Пользователи без поддержки Mini App (старые клиенты, ограниченные регионы) должны иметь полную функциональность через команду `/vote` и взаимодействие с ботом.

**Обоснование**: Mini Apps доступны не повсеместно. Production боты не могут исключать пользователей на основе возможностей клиента. Фолбэк механизмы обеспечивают инклюзивный доступ.

### IV. Целостность данных в реальном времени

Данные опросов НЕ ДОЛЖНЫ НИКОГДА кешироваться в localStorage или клиентском хранилище. Frontend использует React Query с `staleTime: 0` для опросов и агрессивный refetching (интервал 5с для активных опросов). Состояние опроса авторитетно только в базе данных.

**Обоснование**: Устаревшие данные опросов вызывают критические проблемы UX (голосование в закрытых опросах, просмотр устаревших результатов). Пользователи взаимодействуют через множество точек входа (группа, личный чат, Mini App), требуя согласованного состояния во всех каналах.

### V. Типобезопасность и валидация схем

Все потоки данных проходят через TypeScript определения типов. API запросы и ответы валидируются через Zod схемы. Доступ к базе данных исключительно через Prisma ORM (никакого raw SQL). TypeScript strict mode включён на frontend и backend.

**Обоснование**: TypeScript ловит ошибки интеграции на этапе компиляции. Zod обеспечивает runtime валидацию, предотвращая попадание неправильных данных в сервисы. Prisma предотвращает SQL injection и обеспечивает type-safe операции с БД.

### VI. Безопасность прежде всего

Аутентификация Telegram Mini App ДОЛЖНА валидироваться на сервере через HMAC-SHA256 с bot token как секретным ключом (согласно `backend/src/api/middleware/telegram-auth.ts`). Флаг `SKIP_TELEGRAM_VALIDATION` ДОЛЖЕН быть false в production. JWT токены для управления API сессиями. CORS ограничен конкретными origins.

**Обоснование**: Клиентские данные недоверенные. Telegram initData может быть подделан, если не валидирован криптографически. Обход аутентификации создаёт уязвимости безопасности, позволяя имперсонацию и неавторизованные действия.

### VII. Мультирежимный конвейер разработки

Три режима разработки ДОЛЖНЫ поддерживаться: DEV (hot reload), PROD-DEV (production сборки с отладкой), PRODUCTION (полная оптимизация). Каждый режим имеет изолированные файлы окружения (`.env.development`, `.env.prod-dev`, `.env.production`). Скрипты запуска автоматически настраивают правильное окружение.

**Обоснование**: Разные фазы разработки имеют разные потребности. Активная работа над UI требует мгновенной обратной связи (DEV). Тестирование production сборки требует скомпилированного кода, но с видимостью отладки (PROD-DEV). Финальная валидация требует строгой production конфигурации (PRODUCTION). Подход с одним режимом замедляет разработку или пропускает production проблемы.

## Технические стандарты

### Требования к тестированию

- Unit тесты для всех методов сервисов (backend)
- Integration тесты для критических потоков (жизненный цикл опроса, голосование, уведомления)
- Contract тесты для API endpoints
- Flow тесты для end-to-end сценариев (`backend/scripts/test-app-flow.js`)
- Frontend компонентные тесты через Vitest
- Чеклист ручного тестирования перед деплоем (`docs/05-testing/TESTING_GUIDE_FULL.md`)

### Ограничения базы данных

- SQLite для разработки и small-scale production
- Prisma миграции для всех изменений схемы (никакого ручного SQL)
- Бэкап перед запуском миграций
- Файл базы данных: `backend/prisma/dev.db`
- Seeders для пунктов меню и тестовых данных

### Стандарты производительности

- Code splitting frontend через React.lazy()
- Virtual scrolling для длинных списков
- Optimistic updates для действий пользователя
- Debounced поисковые инпуты (300ms)
- Lazy loading изображений
- React Query кеширование с умной инвалидацией

### Критерии качества кода

- Принудительное применение ESLint + Prettier
- TypeScript strict mode (никакого implicit any)
- Async/await предпочтительнее raw promises
- Только функциональные React компоненты (hooks)
- Winston logger для backend событий (никакого console.log в production)
- Error boundaries для React компонентов

## Процесс разработки

### Стратегия веток

- Основная ветка: `main`
- Feature ветки: `feature/<описание>`
- Никогда не коммитить напрямую в main
- Pull requests обязательны для всех изменений

### Настройка окружения

1. Node.js 18+ обязателен
2. ngrok для HTTPS туннеля в разработке
3. Bot token от @BotFather
4. Зависимости backend и frontend установлены раздельно
5. База данных инициализирована через `npm run db:push`
6. Меню засеяно через `npm run db:seed`

### Чеклист перед коммитом

- Тесты проходят (`npm test` в frontend и backend)
- Линтинг проходит (`npm run lint`)
- TypeScript компилируется без ошибок
- Ручной smoke test изменённой функциональности
- Никаких `.env` файлов с реальными токенами не закоммичено
- Документация обновлена, если изменились API или команды

### Процесс деплоя

1. Production сборка frontend (`npm run build`)
2. Компиляция backend (`npm run build`)
3. Миграции базы данных на production БД (`npm run db:migrate:prod`)
4. Установлены переменные окружения (production .env)
5. Telegram webhook настроен на production URL
6. Кнопка меню бота установлена через BotFather
7. Health check endpoint проверен
8. Мониторинг и логирование подтверждены как работающие

## Управление

### Процесс внесения изменений

1. Предлагаемые изменения документируются в pull request
2. Обоснование для поправки предоставлено
3. Влияние на существующий код оценено
4. Определён version bump (MAJOR/MINOR/PATCH)
5. Обновлены зависимые шаблоны (plan, spec, tasks)
6. Файл конституции обновлён с отчётом о синхронизации
7. Требуется одобрение перед merge

### Политика версионирования

Конституция следует semantic versioning:

- **MAJOR**: Удаление принципа, переопределение или обратно-несовместимое изменение управления
- **MINOR**: Добавлен новый принцип, расширение раздела, новая обязательная практика
- **PATCH**: Уточнения, улучшения формулировок, исправление опечаток

### Проверка соответствия

- Все pull requests должны проверять соответствие конституции
- Нарушения требуют явного обоснования в секции Complexity Tracking файла plan.md
- Более простые альтернативы должны рассматриваться и документироваться перед принятием сложности
- Конституция имеет приоритет над неформальными практиками и недокументированными соглашениями

### Руководство по применению

- Разработчики должны обращаться к `CLAUDE.md` для операционного руководства и общих задач
- `README.md` предоставляет обзор проекта и быстрый старт
- Директория `docs/` содержит детальную документацию по реализации
- Конституция определяет неоспоримые принципы; документы-руководства предоставляют практическое применение
