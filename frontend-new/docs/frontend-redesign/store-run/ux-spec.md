# Store Run — UX-спецификация (Phase 3A)

Расширяет и заменяет черновой [../store-run-design.md](../store-run-design.md).
Источники истины: [../store-run-state-machine.md](../store-run-state-machine.md) (аудит бэкенда с file:line),
`src/hooks/useStoreRun.ts`, `src/services/store-run.service.ts`.
Backend/API в Phase 3 не меняем.

## Общая модель экрана

Store Run — не дашборд, а **один рабочий процесс с чёткой фазой**. Экран
=`status`-машина: `COLLECTING → SHOPPING → SETTLED`, ветка `→ CANCELLED`.
Серверный `status` — единственный источник истины (`collectUntil` сам UI в
SHOPPING не переводит: cron отстаёт до минуты).

Композиция (в DetailLayout из Phase 2B, отдельного брендового header нет):

- **ScreenHeader**: `storeName` (title) + `Status` статуса закупки (action-слот).
- **Основной контент**: плоские секции, разделённые `Divider`/отступами, без
  карточки вокруг каждого блока, без glass/glow/градиентов/FAB/вложенных карточек.
- **Закреплённая снизу CTA-зона** (sticky над safe-area): одна главная кнопка
  фазы (или её нет в терминальных состояниях).

### Что понятно за 2–3 секунды

| Статус | Мгновенно ясно | Главное действие |
|---|---|---|
| COLLECTING | куда, сколько осталось до закрытия сбора, сколько позиций | добавить свою позицию (участник) / закрыть сбор (инициатор) |
| SHOPPING | сколько обработано из скольких, что осталось купить | отметить куплено/не нашли, затем «Рассчитать» (инициатор) |
| SETTLED | сколько я должен/мне должны, что куплено | нет (read-only) |
| CANCELLED | что закупка не состоялась | нет (read-only) |

Вторичная информация (имя инициатора, точное время `collectUntil`, заметки к
позициям, аватары) присутствует, но не конкурирует с главным по весу.

### Взаимодействия по типу

- **Inline** (без оверлея): в SHOPPING отметка «Куплено»/«Не нашли» и ввод цены
  прямо в строке; переключение BOUGHT↔NOT_FOUND.
- **BottomSheet**: добавление позиции (`AddStoreItemSheet`), редактирование своей
  (`EditStoreItemSheet`).
- **ConfirmDialog**: удаление позиции, отмена закупки, раннее закрытие сбора,
  «Рассчитать» при наличии REQUESTED.

### Визуальные правила

Используем: плоские секции, вертикальный ритм, разделители, полноширинные
строки-цели (вся строка кликабельна), крупные tap-targets (≥44px), компактные
`Status`, одну CTA-зону снизу.

Не используем: glass, glow, декоративные градиенты, карточку вокруг секции, FAB,
speed-dial, вложенные карточки, staggered-анимацию каждого элемента.

## Ключевые доменные решения (неизменяемая семантика)

1. `price` — итоговая цена **за всю строку**, не за единицу; `quantity`
   информационно. Итог/долги = сумма `price` без умножения на `quantity`
   (budget.service.ts:1472).
2. Редактировать/удалять позицию — **только владелец**; инициатор чужие не
   трогает (service.ts:248, :288). → удаляем баг B2 (корзина на чужих у инициатора).
3. Цену/статус позиции меняет **только инициатор в SHOPPING** (service.ts:338).
   BOUGHT и NOT_FOUND, возврата в REQUESTED через API нет (controller.ts:36).
4. `settle` не отдаёт breakdown — считаем на клиенте из `items` (Q7 аудита).
5. REQUESTED в settle не попадают (budget.service.ts:1460) — предупреждаем.
6. Лимит активной закупки — на инициатора, не на группу.

## Группировка позиций — решения с обоснованием

- **COLLECTING → по участникам, «Мои позиции» первой секцией.** Ментальная
  модель участника здесь — «добавилось ли моё». Группировка по владельцу
  отвечает на этот вопрос напрямую.
- **SHOPPING → единый чеклист, сгруппированный по статусу обработки**
  (Осталось / Куплено / Не нашли), владелец — вторичной подписью в строке.
  Инициатор идёт по магазину и думает «что ещё не куплено», а не «чьё это».
  Группировка по участникам фрагментировала бы список «осталось».
- **Переключателя порядка не добавляем** — реальной пользы нет, лишний контрол.

## Обработка «таймер истёк, статус ещё COLLECTING»

- Показать `InlineNotice` «Сбор закрывается…»; выполнить одноразовый refetch
  detail при переходе `isExpired` (плюс уже идущий poll 15s).
- Локально в SHOPPING **не переводить**.
- Добавление позиций **оставить включённым** (сервер ещё примет до перехода
  cron), но предупредить нотисом. Обоснование: блокировать локально — значит
  разойтись с источником истины и отклонить валидное добавление; предупреждение
  задаёт ожидание без риска.

## Решения по открытым вопросам (утверждены)

- **OQ1.** SETTLED: вторичная кнопка **«На главную»** в конце контента (не в
  sticky CTA). Формулировку «К расчётам» не использовать — отдельного
  budget-экрана нет.
- **OQ2.** CANCELLED: тоже вторичная кнопка **«На главную»** в конце контента.
  Создание новой закупки в терминальный экран не встраиваем.
- **OQ3.** Добавление в COLLECTING — **одна позиция за раз**. Bulk-add (backend
  принимает 1..20 в одном POST) — будущее улучшение.

## CTA-зоны COLLECTING (без конкурирующих primary)

- **Участник**: sticky primary «Добавить позицию».
- **Инициатор**: sticky primary **«Закрыть сбор»**; «Добавить позицию» —
  secondary в секции «Мои позиции»; «Отменить закупку» — destructive secondary.
  Двух конкурирующих primary-кнопок на экране быть не должно.

## CANCELLED — формулировка (уверенная)

Ручной cancel из SHOPPING API не разрешает (только из COLLECTING), поэтому по
`shoppingAt` причина определяется однозначно, без «вероятно»:
- `shoppingAt == null` → «Отменено инициатором».
- `shoppingAt != null` → «Отменено автоматически: расчёт не был завершён вовремя».

## SETTLED summary — role-aware

- **Участник**: «Ваша часть» (`personalDebtTotal`) + «Итого закупки»
  (`purchasedTotal`).
- **Инициатор**: «Вам должны» (`receivableTotal`) + «Ваши покупки»
  (`initiatorOwnTotal`) + «Итого закупки» (`purchasedTotal`). Стоимость
  собственных позиций инициатора — НЕ долг (`personalDebtTotal` для инициатора = 0).
