### Читаемый пример — и в нём проблема не там, где кажется

`poll.service.cancelExpiredPolls` (`backend/src/services/poll.service.ts:243-267`):

```ts
const active = await prisma.poll.findMany({ where: { status: 'ACTIVE' }, ... });   // :244-247
const expired = active.filter(p => p.startedAt.getTime() + p.duration * 60_000 <= now.getTime());  // :248-250
for (const p of expired) {
  const res = await prisma.poll.updateMany({ where: { id: p.id, status: 'ACTIVE' }, ... });
  ...   // :258-267 — побочные эффекты
}
```

Цикл здесь бросается в глаза, но он идёт по **просроченным** опросам, а их
единицы. Настоящая цена — **строки 244–250**: выбираются *все* активные опросы
без фильтра по времени, а отсечение по времени делается в JavaScript. Это
растёт линейно от числа активных опросов, а не от числа просроченных, и
исправляется одним условием в `where`.

Вывод, который стоит держать в голове по всем 39 находкам: статический анализ
находит «запрос в цикле», а дорого бывает «выборка без фильтра перед циклом».
Смотрите на оба.

Про сам цикл: `where` включает `status: 'ACTIVE'` — это **защита от гонки**
(обновится только если статус ещё активен). Наивная замена на один `updateMany`
по списку id эту защиту сохранит, но потеряет **пер-опросные побочные эффекты**
из тела цикла. Смотрите подводные камни.

## Что делать — урезанный объём

**Взять три-четыре находки, а не 39.** Средний `performance` по репозиторию
9.94/10; строить инфраструктуру измерения числа запросов ради 15 находок —
это и есть оверинжиниринг. Берём только то, что на деньгах и на
пользовательском пути:

1. `poll.service.ts:244-250` — выборка всех активных опросов без фильтра по
   времени (см. выше). **Это не находка `io_in_loop`** — запрос там один и до,
   и после правки, поэтому тест «число запросов не зависит от N» здесь
   бессмыслен. Критерий приёмки другой: **число возвращённых строк** —
   выбираются только просроченные, а не все активные.
2. `services/order-calculation.service.ts` — расчёт долей, деньги.
3. `services/category-order.service.ts` — 2 находки `medium`, самый нагруженный
   сценарий закупок.
4. `jobs/debt-reminder.job.ts` — ежедневный джоб, растёт от числа должников.

Остальное — оставить как есть; решение зафиксировано в этом документе, а не
комментариями в 12 файлах. Единственное исключение — `deleteStoreRunMessages`:
там комментарий нужен, потому что находка **принципиально** неустранима
(Telegram не даёт батч-удаления), и без пометки к ней будут возвращаться.

Точные адреса остальных находок, если понадобятся:
`get_health(targets=[...], include=["performance"])` даёт `function_name`,
`line_start`, `line_end` и `boundary_kind` (`db` / сеть).

Приёмы, по порядку применимости:
   - `findMany({ where: { id: { in: ids } } })` вместо цикла `findUnique`;
   - `include`/`select` вместо доп. запроса на связь;
   - `createMany` / `updateMany` вместо цикла;
   - `Promise.all` — **только** для сетевых вызовов (Telegram API), не для БД:
     параллельные запросы к одному пулу соединений дают деградацию, а не
     ускорение.

Затем зафиксировать результат тестом — но критерий у пункта 1 **другой**, чем у
остальных трёх (см. ниже).

## TDD-порядок

Тест на количество запросов — единственный способ не дать N+1 вернуться. Но
писать его стоит **только для четырёх выбранных находок**: счётчик запросов
это инфраструктура, и разворачивать её ради каждой из 39 находок не окупается.

```ts
it('cancelExpiredPolls: число запросов не зависит от числа опросов', async () => {
  const spy = countPrismaCalls();          // счётчик через $on('query') или мок клиента
  await seedExpiredPolls(3);
  await PollService.cancelExpiredPolls();
  const withThree = spy.count();
  spy.reset();
  await seedExpiredPolls(30);
  await PollService.cancelExpiredPolls();
  expect(spy.count()).toBeLessThan(withThree * 3);   // не линейно
});
```

Такой тест падает на текущем коде — это и есть доказательство.

## Подводные камни

- **Побочные эффекты в теле цикла.** Почти во всех перечисленных местах цикл
  делает не только запрос: логирует, отправляет уведомление, публикует событие
  в `event-bus`. Батчинг запроса **не отменяет** необходимости выполнить эти
  эффекты для каждого элемента. Типовая регрессия: заменили цикл на
  `updateMany`, а уведомления перестали уходить. Разделяйте: один батч-запрос,
  затем цикл только по эффектам.
- **Защита от гонки в `where`.** Условия вида `where: { id, status: 'ACTIVE' }`
  — это оптимистическая блокировка. При переходе на батч сохраняйте условие в
  `where` (`{ id: { in: ids }, status: 'ACTIVE' }`) и **проверяйте `count` в
  ответе**: если обновилось меньше, чем ожидалось, часть записей уже изменил
  кто-то другой, и эффекты для них выполнять нельзя.
- **`Promise.all` по Telegram API упрётся в rate limit.** Bot API даёт ~30
  сообщений в секунду и 1 сообщение в секунду в один чат. `sendPersonalNotifications`
  в `poll.service.extensions` уже отправляет через `Promise.all` — при
  расширении на большие группы это начнёт получать 429. Здесь правильное
  направление обратное: не параллелить сильнее, а добавить ограничитель
  скорости. Не путайте эти два случая.
- **`deleteStoreRunMessages`** (`notification.service.ts`) удаляет ЛС по одному
  в цикле — это сеть, а не БД, и Telegram не даёт батч-удаления. Здесь
  оптимизировать нечего; находку можно закрыть как «не применимо», но
  зафиксировать это в коде комментарием, чтобы следующий не искал заново.
- **Не смешивать с задачами 06/07/08.** Изменение запросов одновременно с
  переносом кода между файлами делает регрессию неразличимой.
- **`performance_score` не входит в headline health.** Улучшение этих находок
  не поднимет основной скор файла — не ждите этого и не считайте отсутствие
  роста провалом.

## Что выяснилось при исполнении

Дата: 2026-08-23. Сделаны все четыре правки плюс пометка
`deleteStoreRunMessages`. Ниже — расхождения с планом и решения, которые план
не предусматривал.

**1. `cancelExpiredPolls` — адрес в плане устарел, а фильтр не выражается
через Prisma.** Метод живёт не в `poll.service.ts:244-267`, а в
`services/poll-completion.service.ts` (переехал в задаче 06). Главное же в том,
что срок жизни хранится как `startedAt` + `duration` минут: отбор просроченных
— это сравнение колонки с колонкой, и `where` у Prisma его не выражает. План
говорил «исправляется одним условием в `where`» — через Prisma не исправляется
никак. Пришлось взять `$queryRaw`:

```sql
WHERE status = 'ACTIVE'
  AND started_at + (duration * INTERVAL '1 minute') <= to_timestamp(...) at time zone 'UTC'
```

Ограничить выборку в рамках Prisma можно было бы только грубо — «начато не
позже, чем `at` минус минимальная длительность», а минимальная длительность по
схеме валидации равна **1 минуте** (`duration: min(1).max(1440)`), то есть
такой фильтр не отсекал бы почти ничего.

Момент сравнения уходит в запрос **числом** (epoch ms), а не как `Date`:
`started_at` — это `timestamp(3)` без зоны, куда Prisma пишет UTC, а параметр
типа `Date` приезжает как `timestamptz` и заставляет привести колонку к зоне
сессии. На сервере с местной зоной граница отмены поехала бы на несколько
часов. Это не гипотетическая придирка, а причина, по которой в коде стоит
`to_timestamp(...) at time zone 'UTC'`.

Построчный `updateMany` в цикле оставлен намеренно и помечен комментарием:
`where: { id, status: 'ACTIVE' }` — оптимистичная блокировка, а `count`
показывает, не закрыл ли голосование кто-то другой. Батч по всем id вернул бы
одно суммарное число и не сказал бы, у каких голосований чистить кэш и что
писать в лог. Строк после правки — единицы.

**Тест против плана.** Тест из раздела «TDD-порядок» здесь неприменим (это
сказано и в самом плане), а граница «ровно в момент истечения» ушла в SQL и на
моке Prisma больше не проверяется. Осталось проверяемым: `poll.findMany` не
вызывается вовсе, в тексте запроса есть условие на срок, параметр — число, и
сравнение нестрогое (`<=`). Это утверждения о запросе, а не о данных;
поведение на границе теперь закрыто только интеграционным прогоном с реальной
БД, которого локально нет.

**Дубль тестов удалён.** `src/services/__tests__/poll.service.test.ts` держал
свой `describe('PollCompletionService.cancelExpiredPolls')`, проверявший
именно JS-фильтрацию. Он удалён, а не переписан: канонический набор — в
`src/__tests__/unit/services/poll.service.test.ts`, и все его утверждения
(гонка, кэш, отсутствие эффектов без просроченных) там уже есть. Это часть
давно висящего пункта «слить два `poll.service.test.ts`».

**2. `order-calculation.service.ts` — находка оказалась в реквизитах, а не в
расчёте долей.** В цикле по должникам вызывался
`UserService.getPaymentInfo(transaction.toUserId)` — запрос на итерацию; `Map`
рядом спасал только от повторов внутри одной рассылки, то есть цена росла от
числа разных ответственных. Добавлен `UserService.getPaymentInfoMany(ids)`:
один `findMany` плюс расшифровка в JS (расшифровка — работа процессора, не
базы). Заодно из `responsibleMap` убраны поля `paymentCard`/`paymentPhone`:
в базе они **зашифрованы**, в сообщение идёт расшифрованный вариант, и держать
рядом два одноимённых поля, из которых одно шифротекст, — это заготовка
будущего бага «в сообщении шифротекст».

**3. `category-order.service.ts` — 2 находки `medium` оказались двумя ветками
одного цикла.** `createCategoryOrders` делал `categoryOrder.create` в цикле по
категориям, в двух ветках (один участник / несколько). Разница между ветками —
два поля, поэтому обе свёрнуты в один список и одну вставку
`createManyAndReturn` (PostgreSQL, Prisma 6.19 — доступно). Порядок строк на
входе сохраняется в ответе, на него опираются и возвращаемое значение, и
события. Логи и события по-прежнему идут на каждый созданный заказ — цикл
эффектов отделён от вставки, как требуют «подводные камни». Пустой список в
базу не идёт вовсе.

**4. `debt-reminder.job.ts` — батч по пачке, а не по всей рассылке.**
`transaction.updateMany` вызывался на каждого должника после отправки письма.
Счётчики теперь поднимаются одним запросом **на пачку** (`CONCURRENCY = 4`),
а не на весь список: между отправкой и записью счётчика есть окно, и падение в
нём приводит к повторному напоминанию тем, кому уже написали. Пачка ограничивает
это окно четырьмя должниками; батч на всю рассылку сделал бы окно во всю
рассылку. Счётчик поднимается только у доставленных писем — иначе неудачная
отправка съедала бы попытку из `maxReminders`. Девять должников: было 9
запросов, стало 3.

### Чего не сделано

- **Инфраструктура счётчика запросов не построена.** Тесты считают вызовы
  конкретных методов мока Prisma (`createManyAndReturn` — один раз на N
  категорий, `updateMany` — три раза на девять должников), а не все запросы
  подряд через `$on('query')`. Для четырёх правок этого достаточно; общий
  счётчик — та самая инфраструктура, от которой план предлагал отказаться.
- **Остальные ~35 находок не тронуты**, включая 4 в
  `multi-category-responsible.service.ts` и 4 в `quest.service.ts` из
  «приоритета 1». Решение плана «взять четыре» соблюдено буквально.
- **`performance_score` не перемерян**: индекс Repowise отстаёт от HEAD, а
  `repowise update` запускается человеком. Ожидать роста headline-скора и не
  стоило — в него `performance` не входит.
- **Проверка на реальной БД не выполнена**: `npm --prefix backend test`
  требует PostgreSQL, которого в этой среде нет. Прогнан
  `npm --prefix backend run test:unit` (130 наборов, 3774 теста), плюс `lint` и
  `build:prod`. Сырой SQL в `cancelExpiredPolls` — единственное место в этих
  правках, которое юнит-тестами проверяется лишь по тексту запроса; его стоит
  прогнать на интеграционном окружении отдельно.
