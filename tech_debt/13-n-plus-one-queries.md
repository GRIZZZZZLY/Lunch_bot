# 13 — 39 находок «запрос в цикле» / N+1

- **Приоритет:** P2
- **Оценка:** 0.5 дня в урезанном объёме (3–4 находки на деньгах и
  пользовательском пути), остальное — закрыть как «не применимо»
- **Тип:** производительность
- **Область:** `backend/src/services/*`, `backend/src/jobs/*`
- **Метод:** тест на число запросов (счётчик), затем правка

## Сводка

`get_health` даёт 39 открытых находок класса `io_in_loop` (запрос к БД или
сетевой вызов внутри цикла), плотность 4.26 на 10k строк. Средний
`performance` по репозиторию 9.94 — то есть проблема **точечная, не системная**.
Поэтому чинить надо не все 39, а те, что лежат на пользовательском пути.

### Читаемый пример — и в нём проблема не там, где кажется

`poll.service.cancelExpiredPolls` (`backend/src/services/poll.service.ts:243-267`):

```ts
const active = await prisma.poll.findMany({ where: { status: 'ACTIVE' }, ... });   // :244-247
const expired = active.filter(p => p.startedAt.getTime() + p.duration * 60_000 <= now.getTime());  // :248-250
for (const p of expired) {
  const res = await prisma.poll.updateMany({ where: { id: p.id, status: 'ACTIVE' }, ... });
  ...   // :258-267 — побочные эффекты
}
```

Цикл здесь бросается в глаза, но он идёт по **просроченным** опросам, а их
единицы. Настоящая цена — **строки 244–250**: выбираются *все* активные опросы
без фильтра по времени, а отсечение по времени делается в JavaScript. Это
растёт линейно от числа активных опросов, а не от числа просроченных, и
исправляется одним условием в `where`.

Вывод, который стоит держать в голове по всем 39 находкам: статический анализ
находит «запрос в цикле», а дорого бывает «выборка без фильтра перед циклом».
Смотрите на оба.

Про сам цикл: `where` включает `status: 'ACTIVE'` — это **защита от гонки**
(обновится только если статус ещё активен). Наивная замена на один `updateMany`
по списку id эту защиту сохранит, но потеряет **пер-опросные побочные эффекты**
из тела цикла. Смотрите подводные камни.

## Что делать — урезанный объём

**Взять три-четыре находки, а не 39.** Средний `performance` по репозиторию
9.94/10; строить инфраструктуру измерения числа запросов ради 15 находок —
это и есть оверинжиниринг. Берём только то, что на деньгах и на
пользовательском пути:

1. `poll.service.ts:244-250` — выборка всех активных опросов без фильтра по
   времени (см. выше). **Это не находка `io_in_loop`** — запрос там один и до,
   и после правки, поэтому тест «число запросов не зависит от N» здесь
   бессмыслен. Критерий приёмки другой: **число возвращённых строк** —
   выбираются только просроченные, а не все активные.
2. `services/order-calculation.service.ts` — расчёт долей, деньги.
3. `services/category-order.service.ts` — 2 находки `medium`, самый нагруженный
   сценарий закупок.
4. `jobs/debt-reminder.job.ts` — ежедневный джоб, растёт от числа должников.

Остальное — оставить как есть; решение зафиксировано в этом документе, а не
комментариями в 12 файлах. Единственное исключение — `deleteStoreRunMessages`:
там комментарий нужен, потому что находка **принципиально** неустранима
(Telegram не даёт батч-удаления), и без пометки к ней будут возвращаться.

Точные адреса остальных находок, если понадобятся:
`get_health(targets=[...], include=["performance"])` даёт `function_name`,
`line_start`, `line_end` и `boundary_kind` (`db` / сеть).

Приёмы, по порядку применимости:
   - `findMany({ where: { id: { in: ids } } })` вместо цикла `findUnique`;
   - `include`/`select` вместо доп. запроса на связь;
   - `createMany` / `updateMany` вместо цикла;
   - `Promise.all` — **только** для сетевых вызовов (Telegram API), не для БД:
     параллельные запросы к одному пулу соединений дают деградацию, а не
     ускорение.

Затем зафиксировать результат тестом — но критерий у пункта 1 **другой**, чем у
остальных трёх (см. ниже).

## TDD-порядок

Тест на количество запросов — единственный способ не дать N+1 вернуться. Но
писать его стоит **только для четырёх выбранных находок**: счётчик запросов
это инфраструктура, и разворачивать её ради каждой из 39 находок не окупается.

```ts
it('cancelExpiredPolls: число запросов не зависит от числа опросов', async () => {
  const spy = countPrismaCalls();          // счётчик через $on('query') или мок клиента
  await seedExpiredPolls(3);
  await PollService.cancelExpiredPolls();
  const withThree = spy.count();
  spy.reset();
  await seedExpiredPolls(30);
  await PollService.cancelExpiredPolls();
  expect(spy.count()).toBeLessThan(withThree * 3);   // не линейно
});
```

Такой тест падает на текущем коде — это и есть доказательство.

## Подводные камни

- **Побочные эффекты в теле цикла.** Почти во всех перечисленных местах цикл
  делает не только запрос: логирует, отправляет уведомление, публикует событие
  в `event-bus`. Батчинг запроса **не отменяет** необходимости выполнить эти
  эффекты для каждого элемента. Типовая регрессия: заменили цикл на
  `updateMany`, а уведомления перестали уходить. Разделяйте: один батч-запрос,
  затем цикл только по эффектам.
- **Защита от гонки в `where`.** Условия вида `where: { id, status: 'ACTIVE' }`
  — это оптимистическая блокировка. При переходе на батч сохраняйте условие в
  `where` (`{ id: { in: ids }, status: 'ACTIVE' }`) и **проверяйте `count` в
  ответе**: если обновилось меньше, чем ожидалось, часть записей уже изменил
  кто-то другой, и эффекты для них выполнять нельзя.
- **`Promise.all` по Telegram API упрётся в rate limit.** Bot API даёт ~30
  сообщений в секунду и 1 сообщение в секунду в один чат. `sendPersonalNotifications`
  в `poll.service.extensions` уже отправляет через `Promise.all` — при
  расширении на большие группы это начнёт получать 429. Здесь правильное
  направление обратное: не параллелить сильнее, а добавить ограничитель
  скорости. Не путайте эти два случая.
- **`deleteStoreRunMessages`** (`notification.service.ts`) удаляет ЛС по одному
  в цикле — это сеть, а не БД, и Telegram не даёт батч-удаления. Здесь
  оптимизировать нечего; находку можно закрыть как «не применимо», но
  зафиксировать это в коде комментарием, чтобы следующий не искал заново.
- **Не смешивать с задачами 06/07/08.** Изменение запросов одновременно с
  переносом кода между файлами делает регрессию неразличимой.
- **`performance_score` не входит в headline health.** Улучшение этих находок
  не поднимет основной скор файла — не ждите этого и не считайте отсутствие
  роста провалом.

## Критерии готовности

- [ ] Четыре выбранные правки сделаны.
- [ ] Пункт 1: тест на **число возвращённых строк** (не на число запросов).
- [ ] Пункты 2–4: тест на не-линейность числа запросов + тест на то, что
      побочные эффекты (уведомления, события) выполнились для всех обработанных
      элементов.
- [ ] `deleteStoreRunMessages` помечен в коде «не применимо — Telegram не даёт
      батч-удаления», чтобы к нему не возвращались.

      документа: решение «взяли четыре, остальное отложено» зафиксировано здесь.
