## 15.1 (P1) Путь prod-dev деплоя на VPS уже неработоспособен

`CLAUDE.md` заявляет: «Прежний каталог `frontend/` удалён 2026-08-03; откат к
нему возможен только через git». Фактически каталог существует и содержит
ровно 5 файлов, все — `.env`:

```
frontend/.env  .env.backup  .env.development  .env.prod-dev  .env.production
```

Они **не отслеживаются git'ом** (`.gitignore:7 .env`, `.gitignore:12 .env.*`),
секретов в git не утекло, внутри только `VITE_API_URL`, `VITE_BOT_USERNAME`,
`VITE_NODE_ENV`, `VITE_USE_MOCK_API`.

**Но каталог не «безобидный призрак».** `deploy-prod-dev-vps.sh` на него
опирается:

```sh
:18   test -f frontend/.env.prod-dev
:20   install -m 600 frontend/.env.prod-dev frontend/.env
:31-33  ( cd frontend; npm ci; npx vite build --config vite.config.prod-dev.ts )
```

В каталоге `frontend/` **нет `package.json`** и **нет `vite.config.prod-dev.ts`**.
То есть `npm ci` на строке 32 гарантированно падает: **путь prod-dev деплоя на
VPS мёртв уже сейчас**, независимо от того, удалим мы каталог или нет.

Ещё четыре корневых скрипта ссылаются на `frontend/`:
`start-dev.ps1`, `update-ngrok-url.ps1`, `update-urls-prod.ps1`,
`verify-configs.ps1` (строки 188, 196–197 читают `frontend/dist/index.html`,
которого не существует).

**Что делать — в этом порядке:**

1. **Сначала решить судьбу prod-dev деплоя.**

   - **Не нужен** → удалить скрипт. Это 10 минут, и тогда вся задача — 1 час.
   - **Нужен** → это **0.5 дня, а не час**, потому что готовой команды сборки
     нет. Осторожно: `frontend-new/package.json` содержит
     `"build:prod-dev": "vite build --watch --mode development"` — **это не
     подходит для деплоя**: `--watch` никогда не завершится (выкат повиснет
     навсегда), а `--mode development` даст dev-бандл. И
     `vite.config.prod-dev.ts`, на который ссылается старый скрипт, в
     `frontend-new` **тоже отсутствует** — там только `vite.config.ts`.
     Значит нужно: определить, чем prod-dev отличается от prod (вероятно только
     набором env), выразить это через `--mode` + `.env.prod-dev` в
     `frontend-new/`, и вызывать обычный `vite build` без `--watch`.
     Скрипт `build:prod-dev` в `package.json` при этом стоит переименовать
     (например, в `dev:watch:prod-mode`) — сейчас его имя обещает то, чем он
     не является, и именно на это имя я и попался в первой редакции.
2. Починить или удалить четыре PowerShell-скрипта, ссылающихся на `frontend/`.
3. **Только после этого** удалить каталог `frontend/` (файлы не в git — потери
   нет). Если `.env`-значения нужны как образец — `frontend-new/.env.example`
   без значений.
4. Привести `CLAUDE.md` в соответствие с действительностью.

**Подводный камень:** соблазн начать с шага 3 («это же просто 5 .env-файлов»)
велик — и тогда сломанный деплой станет сломанным **молча и по другой причине**,
что запутает следующего сильнее, чем текущее состояние. Порядок обязателен.

## 15.2 `TECHNICAL_AUDIT_2026-07-19.md` — снимок с датой ✅ СДЕЛАНО

`CLAUDE.md` прямо запрещает такие файлы: «Обновляйте существующий живой документ

Документ нарушал собственное правило проекта и удалён 2026-08-22.

### Что из него перенесено

**1. Не закрытое действие по безопасности — вынесено в
[README](README.md#открытые-действия-вне-задач-каталога).** В служебных
сценариях и документации нашли два похожих на действующие токена Telegram.
Значения из файлов убрали, но **в истории git они остались**, поэтому оба токена
надо отозвать через BotFather. Полное вычищение из истории — отдельная
согласованная операция с перезаписью. Это единственная находка аудита, которая
требовала действия и никем не была закрыта; в каталоге её не было вовсе.

**2. Принятый риск в зависимостях.** `npm audit --audit-level=high` зелёный на
обоих пакетах. На сервере остаются **три средние** уязвимости в транзитивной
зависимости `@hono/node-server`, которую тянет только средство разработки
Prisma. Предлагаемое npm исправление понижает Prisma до 6 — поэтому **намеренно
не применялось**. Записано, чтобы следующий не «починил» это понижением.

**3. Ограничения локальной среды — два, а не одно.**

- Lighthouse на Windows не укладывается в 60 секунд из-за запуска Chrome;
  конфигурация и пороги живут только как этап Linux CI (производительность
  ≥ 0,80, доступность и best practices ≥ 0,90, SEO ≥ 0,80). Локальный красный
  Lighthouse на Windows — не регрессия.
- **Серверные тесты локально не запускаются целиком:** `globalSetup` требует
  PostgreSQL `foodbot_test_db` на `localhost:5432` и останавливает прогон, если
  база недоступна. CI — единственная среда, где база поднимается, поэтому
  порог покрытия (`branches 88 / functions 89 / lines 94 / statements 94`)
  меряется только там. Локально работает `npm --prefix backend run test:unit`
  (конфиг `jest.unit.config.js`, без `globalSetup`) — он покрывает юнит-тесты,
  но НЕ интеграционные и НЕ считает покрытие.

**4. Знаменатель порога покрытия фронтенда.** Порог применяется к критическому
прикладному контуру: службам заказов, магазина, пожертвований, администрирования
и геймификации плюс ключевым пользовательским и административным компонентам.
Конфигурационные файлы, истории Storybook и декларации типов в знаменатель
**не входят** — то есть «покрытие 90%» относится не ко всему `frontend-new`.
Пригодится в задаче [11](11-frontend-test-coverage.md).

Остальное содержимое было отчётом о уже выполненной работе (строгий TypeScript,
CI, Knip, пороги покрытия) — то есть ровно тем, что `CLAUDE.md` и запрещает
хранить. Два наблюдения, полезных другим задачам каталога, перенесены как
ссылки в [10](10-any-on-api-boundary.md) и [12](12-homepage-god-component.md).

`DESIGN.md`, `docs/superpowers/` и разбор 24 корневых скриптов из этой задачи
**исключены сознательно**: объём неограничен, отдача для кода нулевая.
`docs/superpowers/` намеренно оставлен без рекомендации: я его не читал, а
удалять непрочитанное нельзя. Если кто-то посмотрит и увидит там служебные
материалы агента — удаление занимает 2 минуты, но это отдельное решение и в
критерии готовности данной задачи не входит.

## 15.3 Vitest: TODO не наступил — просто зафиксировать

`frontend-new/vite.config.ts`:

```ts
cache: false,
fileParallelism: false,
pool: 'forks',
// TODO(infra): перепроверить после обновления Vitest > 4.1.x.
```

Комментарий описывает, почему так: три наложившихся сбоя (битый
optimizer-кэш, гонка воркеров, баг tinypool с worker_threads на Windows).
Настройка правильная — детерминированность важнее скорости.

**Установленная версия — ровно `4.1.10`** (по `frontend-new/package-lock.json`;
в `package.json` стоит диапазон `^4.1.10`, на него ссылаться нельзя), то есть
условие «> 4.1.x» **не выполнено**. Действие сводится к одному: **дописать в
комментарий, что на 4.1.10 проверено и условие не наступило**, чтобы следующий
не выяснял это заново. Настройку не трогать.

Оговорка, без которой запись быстро станет ложной: диапазон в `package.json` —
`^4.1.10`, то есть следующий `npm install` может подтянуть 4.2.x, условие TODO
наступит само, а комментарий будет утверждать обратное. Либо запишите
«проверено на 4.1.10 (lock)», либо запиньте версию точно.

Если версия когда-нибудь вырастет: включать параллелизм **только целиком**
(не `fileParallelism: true` при сохранённом `pool: 'forks'` — симптом был
составным, частичное включение даст «иногда падает») и прогонять **не менее
5 раз подряд** — сбой был плавающим, один зелёный прогон ничего не доказывает.

## Замечание для следующего

Эту задачу пришлось править **дважды**, ревью дало 3/10, затем 7/10, и оба раза
по одной причине: **список затронутых файлов брался из шаблона поиска, который
казался достаточным.**

- План утверждал «ровно четыре скрипта». Он получил это поиском по `frontend/`
  — шаблон не видит `frontend\` в PowerShell.
- Второй проход добавил `frontend\`, bare `frontend` после
  `cd`/`Set-Location`/`Push-Location`/`Join-Path` — и нашёл девять файлов
  вместо четырёх. Всё равно пропустил `"cd '$projectRoot\frontend'"`
  (переменный префикс), `directory: /frontend` в `dependabot.yml`,
  `context: ./frontend` в `docker-compose.yml` и рецепт восстановления в
  `scripts/backup.ps1`.
- Сработал только отказ от шаблонов «путь выглядит так»: искать **все**
  вхождения слова и отсеивать глазами.

Второй вывод: зелёные `npm test`/`npm run build` тут не доказывают ничего.
В `frontend-new` менялся только комментарий, а сломаны были скрипты и конфиги,
которые не запускает ни один тест. Именно поэтому раздел «Подводный камень»
выше требовал закончить шаг 2 **до** удаления каталога, а не после.

**Оставлено намеренно, требует внимания владельца:** `test -f` для
`$FRONTEND_DIR/.env.$ENV_SUFFIX` теперь жёсткий и для `production` тоже. Это
ужесточение P0-пути: файл под `.gitignore`, и если на VPS
`frontend-new/.env.production` отсутствует, следующий выкат упадёт там, где
раньше молча продолжал на env предыдущего выката. Молчаливое продолжение —
худший из двух вариантов, но проверить наличие файла на стенде надо до
следующего деплоя.
