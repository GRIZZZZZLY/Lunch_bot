## Что не так

`backend/src/api/middleware/validation.ts` (332 строки) — готовый слой валидации
на zod. Используется он в **одном** файле:

| route-файл | вызовов валидации |
|---|---|
| `menu.routes.ts` | 2 (`validateMenuItemData` на строках 52 и 64) |
| **остальные 21 файл** | **0** |

Осторожно с `auth.routes.ts`: там есть `router.post('/validate', ...)` — это
**эндпоинт с путём `/validate`** (`authController.validateInitData`), а не
middleware валидации. Наивный grep по слову `validate` даёт ложное срабатывание.

Среди «остальных» — `poll.routes.ts` (253 строки, самый нагруженный),
`category-order.routes.ts` (138), `admin.routes.ts` (217),
`budget.routes.ts`, `store-run.routes.ts`, `recurring-poll.routes.ts`,
`season.routes.ts`, `menu-suggestion.routes.ts`.

Вместо валидации контроллеры разбирают вход руками, вперемешку с бизнес-логикой:

```ts
const pollId = parseInt(getParam(req.params, 'pollId'), 10);
if (isNaN(pollId)) {
  res.status(400).json({ success: false, error: 'Invalid pollId', code: 'INVALID_POLL_ID' });
  return;
}
```

Такой блок повторяется десятки раз. Следствия:

1. **`req.body` не проверяется вообще** в большинстве мутаций. Тело уходит в
   сервис и дальше в Prisma. Лишние/неверные поля, `null` вместо числа,
   строка вместо массива — всё это обнаруживается уже как исключение Prisma,
   которое `error-handler` превратит в 500 вместо 400.
2. Каждый handler на 25–185 строк начинается с 10–30 строк парсинга — это
   основной вклад в размер контроллеров (см. задачи 05 и 08).
3. Коды ошибок расходятся (`INVALID_POLL_ID`, `INVALID_ID`, `BAD_REQUEST` для
   одного и того же класса ошибок).

## Готовые кирпичи, о которых легко не узнать

`validation.ts` экспортирует **7** функций. Продакшен-вызовов имеет **одна**:

| Экспорт | Строка | Продакшен-вызовов | Тесты |
|---|---|---|---|
| `validateMenuItemData` | 48 | 2 | есть |
| `validatePollData` | 100 | **0** | есть |
| `validateVoteData` | 140 | **0** | есть |
| `validateIdParam` | 180 | **0** | есть |
| `validatePaginationParams` | 212 | **0** | есть |
| `validateWithSchema(schema)` | 261 | **0** | есть |
| `sanitizeStrings` | 299 | **0** | есть |

Все шесть неиспользуемых **полностью покрыты тестами**
(`backend/src/__tests__/unit/middleware/validation.test.ts`, строки ~313–650).
То есть: код написан, протестирован и не подключён — а его покрытие входит в
те самые 94.26%, ничего при этом не защищая.

Практический вывод: **не пишите схемы с нуля** — но и не наследуйте контракт
этих кирпичей слепо. Что они делают на самом деле (прочитано, не предположено):

- **`validateWithSchema(schema)` валидирует ТОЛЬКО `req.body`**
  (`validation.ts:264`: `schema.safeParse(req.body)`). Ни `params`, ни `query`
  он не трогает и не переписывает.
- **`validateIdParam(name)` НЕ приводит `req.params` к числу.** Он кладёт
  результат в `(req as any).validatedId = id` (`validation.ts:195`) и оставляет
  `req.params` строками. **Читателей у `validatedId` нет ни одного** — то есть
  контракт мёртв в обе стороны, и при подключении его надо выбирать заново
  (положить в `req.params` типизированно или отдать по-другому), а не
  наследовать. Плюс поле **одно на запрос**: на маршруте с двумя
  id-параметрами (`:pollId` + `:categoryOrderId` в category-order) второй
  вызов молча перетрёт первый, и ошибка проявится не 400-м, а **неверным
  объектом**.
- То же про `validatePaginationParams` → `(req as any).pagination`
  (`validation.ts:240`), читателей нет.
- `validatePollData` / `validateVoteData` — проверьте, совпадают ли с текущим
  контрактом; если да, подключение занимает минуты.

**Для `query` готового примитива НЕТ.** Его придётся написать — и это как раз
там, где лежит главный подводный камень задачи (инъекция `groupId`, см. ниже).

**Где держать схемы:** каталога `backend/src/api/schemas/` **не существует** —
не ищите его. Решение принимается один раз: либо штучные middleware-функции
рядом в `validation.ts` (как `validateMenuItemData`), либо zod-схемы в новом
`backend/src/api/schemas/<домен>.ts` + `validateWithSchema`. Второе
предпочтительнее (схема — данные, её можно переиспользовать и на типах), но
выберите одно и не смешивайте.

## Что делать

Не переписывать всё разом. Порядок по риску:

1. `poll.routes.ts` — самый нагруженный и самый часто меняемый.
2. `category-order.routes.ts` — контроллер за ним имеет худший health-скор в репозитории (1.9).
3. `budget.routes.ts`, `store-run.routes.ts` — денежные операции.
4. `recurring-poll.routes.ts`, `menu-suggestion.routes.ts`, `season.routes.ts`.
5. `admin.routes.ts` — последним: там больше всего endpoint'ов и они реже вызываются пользователем.

Для каждого:

- завести схемы в выбранном месте (см. выше) и подключить через
  `validateWithSchema`; для `:id`-параметров использовать готовый
  `validateIdParam('<name>')`;
- подключить `validate*`-middleware в цепочку до контроллера;
- **удалить** соответствующий ручной парсинг из контроллера, а не оставить
  «на всякий случай» — иначе долг вырастет, а не уменьшится;
- **не рассчитывайте, что `parseInt` уйдёт сам.** После `validateWithSchema`
  типизировано только тело; `params` и `query` остаются строками (см. выше).
  Чтобы `parseInt` действительно исчез из контроллеров, нужно решить, куда
  middleware кладёт разобранное значение, и это решение принимается **один
  раз на весь проект**, а не по роутеру.

## Подводные камни

- **Ломка фронтенда.** Фронт местами отправляет поля, которых нет в схеме
  (например, поля, добавленные для отладки). Строгая схема (`.strict()`) их
  отклонит и уронит рабочий сценарий. Сначала прогоните
  `npm --prefix frontend-new run test:e2e:smoke`, посмотрите фактические тела
  запросов, и только потом решайте `strict` или `passthrough`. Для первого
  прохода безопаснее `passthrough` + логирование лишних полей.
- **САМЫЙ ВЕРОЯТНЫЙ СПОСОБ УРОНИТЬ ПРОД ЭТОЙ ЗАДАЧЕЙ — валидация query.**
  `frontend-new/src/services/api.service.ts` в `buildUrl` **автоматически
  подмешивает `groupId` в query каждого запроса**. При этом готового
  query-примитива в `validation.ts` нет (`validateWithSchema` — только тело), то
  есть middleware для query придётся писать с нуля. Если кто-то напишет строгую
  query-схему по образцу body-схемы, **400 полетит одновременно на всех
  endpoint'ах**. Первая query-схема обязана допускать `groupId`, и первый
  прогон — на `passthrough`, не на `strict`.
- **Коды ошибок сначала разойдутся сильнее.** Существующие кирпичи отвечают
  по-разному: `validateIdParam` → `INVALID_ID`, `validateWithSchema` →
  (см. `validation.ts:275+`, там `'Validation failed'`). Фронт ветвится по
  `code` (`frontend-new/src/lib/apiError.ts`, `authRetry.ts`). Значит **словарь
  кодов из задачи 03 нужен ДО контрактных тестов этой задачи** — иначе тесты
  закрепят код, который потом придётся менять, и правка кода станет
  «ломающей тесты», то есть отложится навсегда. В графе зависимостей README
  это учтено: 03 стоит перед 02 по этому пункту.
- **Идемпотентность — два разных риска.**
  `backend/src/api/middleware/idempotency.ts` подключён в 10 route-файлах и
  читает тело до контроллера. Во-первых, порядок: валидация должна стоять
  **после** идемпотентности, иначе ключ считается по невалидированному телу и
  повтор с другим телом попадёт в тот же слот. Во-вторых и важнее: middleware
  **кэширует ответ**. После введения валидации по уже существующим ключам
  начнут отдаваться закэшированные `200` там, где теперь должен быть `400` (и
  наоборот, закэшированные `400` — там, где запрос стал валиден). **Сбросить
  кэш идемпотентности при релизе** — обязательный пункт плана выката, иначе
  на проде будут «необъяснимые» ответы в течение TTL.
- **Формат ошибки.** `validation.ts` сейчас отдаёт `success: false` (13 сайтов).
  Не меняйте формат в этой задаче — это задача 03. Иначе два рефакторинга
  наложатся и разбор регрессии станет невозможным.
- **BigInt в params.** `telegramId` в некоторых роутах — строка с числом,
  превышающим `Number.MAX_SAFE_INTEGER`. `z.coerce.number()` там молча
  испортит значение. Для таких полей нужен `z.string().regex(/^\d+$/)`.

## Как сделано

### Решение, принятое один раз на весь проект

`backend/src/api/middleware/validate.ts` — **контракт**: один объект, у которого
есть и `middleware` для роутера, и `get(req)` для контроллера.

```ts
export const pollIdParam = idParams('id');          // schemas/poll.ts
router.get('/:id', auth, pollIdParam.middleware, ctrl.getPollById);
const { id } = pollIdParam.get(req);                // в контроллере
```

Почему так, а не как у `validateIdParam`: рассинхронизация «в роутере одна
схема, в контроллере другая» физически невозможна — это одна и та же ссылка.
Разобранное значение запоминается в `req.validated` по слоту на источник, и слот
помнит СХЕМУ: два разных контракта на один источник не получат чужие данные под
своим типом.

`get()` разбирает вход сам, если middleware не отработал. Это не страховка, а
следствие того, что разбор — одна функция: ответ на невалидный вход одинаков
независимо от того, кто первым его вызвал. Практический смысл — 400+ тестов
контроллеров продолжают вызывать handler напрямую с `params: { id: '1' }`.

**Цена этого решения, о которой надо знать.** Разбор вызывается первой строкой
внутри `try`, поэтому в каждом `catch` контроллера, читающего контракт, стоит
`respondIfInvalidInput(req, res, error)`. Без него исключение разбора попадает в
общий обработчик и превращается в `500 INTERNAL_ERROR` вместо 400 — это не
теория, так упали 42 теста контроллера голосований сразу после переноса.

### Схемы

`backend/src/api/schemas/` (каталога не было — решение из этого файла):
`common.ts` + по файлу на домен. Схема — данные, из неё выводится тип; функция-
middleware ни того, ни другого не даёт.

- **`passthrough`, а не `strict`** — и причина не в лишних полях от фронта.
  По умолчанию zod ВЫРЕЗАЕТ незаявленные ключи, а разобранное тело подменяет
  `req.body`: любое поле, которое схема не перечислила, а контроллер читает,
  тихо стало бы `undefined`.
- **Исключение — два тела со `strict`** (`reminderSettingsBody`,
  `adminNotificationSettingsBody`): они уходят в `prisma.upsert({ update: data })`
  целиком. Лишнее поле там либо давало исключение Prisma и 500, либо, если
  совпадало с колонкой, применялось — а тип на клиенте
  (`Partial<ReminderSettings>`) включает `groupId`, то есть присланный в теле
  `groupId` переписал бы настройки ЧУЖОЙ группы.
- **Код ошибки определяется ИМЕНЕМ параметра** (`PARAM_CODES` в `common.ts`), а
  не маршрутом. Это и есть исправление расхождения, названного выше: за один и
  тот же `:id` контроллеры отдавали то `INVALID_ID`, то `INVALID_POLL_ID`.
  Единственное публичное следствие — `POST /api/polls/repeat/:id` теперь отдаёт
  `INVALID_ID`; текст на фронте у обоих кодов есть.
- **Код на ПОЛЕ, а не только на контракт** (`ContractCode`). Одного кода не
  хватает: `GET /popular-items` отдавал `INVALID_LIMIT` за `limit` и
  `MISSING_GROUP_ID` за `groupId`, и у этих кодов на фронте разные тексты.
  Свернуть их в `VALIDATION_ERROR` значило бы заменить «Укажите группу» на
  «Проверьте заполненные поля».

### Порядок в цепочке

`params`/`query` — сразу после аутентификации: middleware авторизации ниже сами
читают `req.params` и с `NaN` пошли бы в базу за несуществующим ресурсом.
`body` — после идемпотентности: ключ считается по исходному телу.

### Гарантия проводки

`backend/src/__tests__/unit/routes/param-validation.test.ts` обходит
`router.stack` каждого из 8 роутеров и требует:

- контракт `params` на каждом маршруте с `:параметром`;
- контракт `body` на каждой мутации, кроме 16 перечисленных с причиной (ключ
  списка включает имя роутера — пути в разных роутерах совпадают, и `DELETE /:id`
  это и расписание без тела, и предложение блюда с телом);
- порядок слоёв;
- мусор в параметре, теле и query → 400 с указанием поля. Мусор не выдуман, а
  сгенерирован ПО ПОЛЯМ схемы: тест доходит до неё через `middleware.contract`.

Последний пункт появился только после ревью, и это стоит помнить: пока
проверялись одни имена слоёв, тест пропустил два дефекта, ломавших прод (см.
ниже).

## Что нашлось по дороге

Не «попутные улучшения», а дефекты, которые валидация сделала видимыми:

1. **`req.body` уходил в Prisma целиком** — см. выше про `strict`.
2. **4 из 6 zod-схем в `budget.controller.ts` были объявлены и не вызывались
   ни разу** (`PollIdParamSchema`, `StatusQuerySchema`, `DateRangeQuerySchema`,
   `SetOrderCostsSchema`). Подключены. `DateRangeQuerySchema` — не дословно:
   он требовал полный ISO с временем и отверг бы законный `?from=2026-08-01`.
3. **`?daysOld=3O`** (буква O вместо нуля) молча становился 30 днями
   безвозвратного удаления. **`?kind=transaction`** (без s) показывал
   предпросмотр не того, что админ собирался удалять.
4. **Испорченный `?groupId` трактовался как отсутствующий**: список предложений
   молча отдавал только свои вместо ошибки — фильтр, тихо превратившийся в
   другой фильтр.
5. **`selectedMenuItems` «чистился»** через `.map(parseInt).filter(!isNaN)`:
   мусор в списке исчезал, и голосование создавалось по случайному подмножеству
   блюд.
6. **store-run отвечал `{ error, issues }`** — без `code` и без `success`, то
   есть фронт не мог выбрать по нему текст.
7. **Нестроковая причина исключения участника** молча отбрасывалась: админ был
   уверен, что причину записали.
8. **`getGroupId` в админке возвращал 0** при `?groupId=0`, а вызывающие
   проверяют результат на ложность — ответ не отправлялся вовсе.

## Что нашло ревью (и почему тест обязан был найти это раньше)

Оценка первого прохода — 5/10, и справедливо: реализация напоролась ровно на
подводный камень, описанный в этом же файле.

1. **Повторяющийся `groupId` в query → 400 на восьми админских эндпоинтах.**
   `api.service.ts` в `buildUrl` подмешивает `groupId` из стора, а
   `admin.service.ts` и `suggestions.service.ts` уже встроили его в путь.
   Получалось `?groupId=5&groupId=5`; `qs` отдаёт массив, `z.coerce.number()`
   даёт NaN. Работало это раньше по случайности: `parseInt(['5','5'])` приводит
   массив к строке `'5,5'` и возвращает 5.
   Исправлено с двух сторон: `buildUrl` больше не дописывает параметр, уже
   присутствующий в пути, а схема сводит повторяющиеся ОДИНАКОВЫЕ значения к
   одному. РАЗНЫЕ (`?groupId=5&groupId=7`) не сводятся — выбрать одно молча это
   та же подмена. Тот же разбор добавлен в `middleware/group-admin.ts`, где от
   значения зависит решение о доступе.
2. **Строгая схема отвергала тело, которое фронт реально отправляет.**
   `ReminderSettingsCard.tsx` посылает на каждый тумблер ОДНО поле; схема
   требовала все четыре и выключила все четыре переключателя. Урок в одну
   строку: **«строгая» и «обязательная» — разные свойства**, и смешивать их
   нельзя. Теперь `strictPartialBodyShape`; заодно закрылся край, где частичный
   PUT по группе без записи падал 500 (`messageTemplate` без значения по
   умолчанию — подставляется тот же шаблон, что при первом чтении).

Оба закреплены тестами. Общий вывод: структурный тест «слой стоит в цепочке» не
заменяет поведенческий «слой отвечает 400 на то, что реально присылают».

- **`middleware/validation.ts` не тронут.** Шесть неподключённых экспортов с
  тестами остались, теперь рядом со вторым слоем валидации. Удалять их в этой
  задаче не стали осознанно: они полностью покрыты тестами, а запасы по порогам
  покрытия тонкие (94.26/94 statements, 89.3/89 functions), и померить итог можно
  только в CI с PostgreSQL. Это отдельная правка с отдельной проверкой.
- **Сброс кэша идемпотентности при выкате** (пункт из «Подводных камней» выше) в
  коде отражён быть и не может — это шаг плана выката. По уже существующим
  ключам будут отдаваться закэшированные `200` там, где теперь должен быть `400`,
  и наоборот, в течение TTL.
- **Smoke-e2e фронта не прогонялся**: нужен живой backend с PostgreSQL. Вместо

Полный прогон backend падал с «Jest worker ran out of memory» и «Zone Allocation
failed» — на СЛУЧАЙНОМ наборе, то есть красный CI не указывал бы на виновника.
Причина не в одном тесте и посчитана, а не угадана: Jest по умолчанию берёт
`cpus - 1` воркеров (здесь 11), каждый держит свой кэш ts-jest и по нескольку
графов модулей — роутер тянет все контроллеры и сервисы. 11 × ~700 МБ упирается в
доступную память целиком; долго это работало на грани и свалилось от одного
добавленного набора. В `backend/jest.config.js` добавлены `maxWorkers: '50%'` и
`workerIdleMemoryLimit`; пороги покрытия не трогались. Отдельно поправлен и сам
новый тест: он строил приложение и поднимал HTTP-сервер на каждую проверку —
теперь слой вызывается напрямую там, где express не нужен.
