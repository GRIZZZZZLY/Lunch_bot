# 02 — 21 из 22 route-файлов принимают вход без валидации

- **Приоритет:** P0 (корректность + поверхность атаки)
- **Оценка:** 2 дня на 5 приоритетных роутеров; 3–4 дня на все
- **Тип:** архитектурный пробел
- **Область:** `backend/src/api/routes/*`, `backend/src/api/middleware/validation.ts`
- **Метод:** TDD (контрактные тесты на 400)

## Что не так

`backend/src/api/middleware/validation.ts` (332 строки) — готовый слой валидации
на zod. Используется он в **одном** файле:

| route-файл | вызовов валидации |
|---|---|
| `menu.routes.ts` | 2 (`validateMenuItemData` на строках 52 и 64) |
| **остальные 21 файл** | **0** |

Осторожно с `auth.routes.ts`: там есть `router.post('/validate', ...)` — это
**эндпоинт с путём `/validate`** (`authController.validateInitData`), а не
middleware валидации. Наивный grep по слову `validate` даёт ложное срабатывание.

Среди «остальных» — `poll.routes.ts` (253 строки, самый нагруженный),
`category-order.routes.ts` (138), `admin.routes.ts` (217),
`budget.routes.ts`, `store-run.routes.ts`, `recurring-poll.routes.ts`,
`season.routes.ts`, `menu-suggestion.routes.ts`.

Вместо валидации контроллеры разбирают вход руками, вперемешку с бизнес-логикой:

```ts
const pollId = parseInt(getParam(req.params, 'pollId'), 10);
if (isNaN(pollId)) {
  res.status(400).json({ success: false, error: 'Invalid pollId', code: 'INVALID_POLL_ID' });
  return;
}
```

Такой блок повторяется десятки раз. Следствия:

1. **`req.body` не проверяется вообще** в большинстве мутаций. Тело уходит в
   сервис и дальше в Prisma. Лишние/неверные поля, `null` вместо числа,
   строка вместо массива — всё это обнаруживается уже как исключение Prisma,
   которое `error-handler` превратит в 500 вместо 400.
2. Каждый handler на 25–185 строк начинается с 10–30 строк парсинга — это
   основной вклад в размер контроллеров (см. задачи 05 и 08).
3. Коды ошибок расходятся (`INVALID_POLL_ID`, `INVALID_ID`, `BAD_REQUEST` для
   одного и того же класса ошибок).

## Готовые кирпичи, о которых легко не узнать

`validation.ts` экспортирует **7** функций. Продакшен-вызовов имеет **одна**:

| Экспорт | Строка | Продакшен-вызовов | Тесты |
|---|---|---|---|
| `validateMenuItemData` | 48 | 2 | есть |
| `validatePollData` | 100 | **0** | есть |
| `validateVoteData` | 140 | **0** | есть |
| `validateIdParam` | 180 | **0** | есть |
| `validatePaginationParams` | 212 | **0** | есть |
| `validateWithSchema(schema)` | 261 | **0** | есть |
| `sanitizeStrings` | 299 | **0** | есть |

Все шесть неиспользуемых **полностью покрыты тестами**
(`backend/src/__tests__/unit/middleware/validation.test.ts`, строки ~313–650).
То есть: код написан, протестирован и не подключён — а его покрытие входит в
те самые 94.26%, ничего при этом не защищая.

Практический вывод: **не пишите схемы с нуля** — но и не наследуйте контракт
этих кирпичей слепо. Что они делают на самом деле (прочитано, не предположено):

- **`validateWithSchema(schema)` валидирует ТОЛЬКО `req.body`**
  (`validation.ts:264`: `schema.safeParse(req.body)`). Ни `params`, ни `query`
  он не трогает и не переписывает.
- **`validateIdParam(name)` НЕ приводит `req.params` к числу.** Он кладёт
  результат в `(req as any).validatedId = id` (`validation.ts:195`) и оставляет
  `req.params` строками. **Читателей у `validatedId` нет ни одного** — то есть
  контракт мёртв в обе стороны, и при подключении его надо выбирать заново
  (положить в `req.params` типизированно или отдать по-другому), а не
  наследовать. Плюс поле **одно на запрос**: на маршруте с двумя
  id-параметрами (`:pollId` + `:categoryOrderId` в category-order) второй
  вызов молча перетрёт первый, и ошибка проявится не 400-м, а **неверным
  объектом**.
- То же про `validatePaginationParams` → `(req as any).pagination`
  (`validation.ts:240`), читателей нет.
- `validatePollData` / `validateVoteData` — проверьте, совпадают ли с текущим
  контрактом; если да, подключение занимает минуты.

**Для `query` готового примитива НЕТ.** Его придётся написать — и это как раз
там, где лежит главный подводный камень задачи (инъекция `groupId`, см. ниже).

**Где держать схемы:** каталога `backend/src/api/schemas/` **не существует** —
не ищите его. Решение принимается один раз: либо штучные middleware-функции
рядом в `validation.ts` (как `validateMenuItemData`), либо zod-схемы в новом
`backend/src/api/schemas/<домен>.ts` + `validateWithSchema`. Второе
предпочтительнее (схема — данные, её можно переиспользовать и на типах), но
выберите одно и не смешивайте.

## Что делать

Не переписывать всё разом. Порядок по риску:

1. `poll.routes.ts` — самый нагруженный и самый часто меняемый.
2. `category-order.routes.ts` — контроллер за ним имеет худший health-скор в репозитории (1.9).
3. `budget.routes.ts`, `store-run.routes.ts` — денежные операции.
4. `recurring-poll.routes.ts`, `menu-suggestion.routes.ts`, `season.routes.ts`.
5. `admin.routes.ts` — последним: там больше всего endpoint'ов и они реже вызываются пользователем.

Для каждого:

- завести схемы в выбранном месте (см. выше) и подключить через
  `validateWithSchema`; для `:id`-параметров использовать готовый
  `validateIdParam('<name>')`;
- подключить `validate*`-middleware в цепочку до контроллера;
- **удалить** соответствующий ручной парсинг из контроллера, а не оставить
  «на всякий случай» — иначе долг вырастет, а не уменьшится;
- **не рассчитывайте, что `parseInt` уйдёт сам.** После `validateWithSchema`
  типизировано только тело; `params` и `query` остаются строками (см. выше).
  Чтобы `parseInt` действительно исчез из контроллеров, нужно решить, куда
  middleware кладёт разобранное значение, и это решение принимается **один
  раз на весь проект**, а не по роутеру.

## TDD-порядок

На каждый endpoint — контрактный тест до правки:

```ts
it('POST /api/polls/:id/vote с menuItemId="abc" → 400 VALIDATION_ERROR', async () => {
  const res = await request(app).post('/api/polls/1/vote').send({ menuItemId: 'abc' });
  expect(res.status).toBe(400);
  expect(res.body.code).toBe('VALIDATION_ERROR');
});
```

Тест до правки даст 500 (или 200 с мусором в БД) — это и есть доказательство
дефекта.

## Подводные камни

- **Ломка фронтенда.** Фронт местами отправляет поля, которых нет в схеме
  (например, поля, добавленные для отладки). Строгая схема (`.strict()`) их
  отклонит и уронит рабочий сценарий. Сначала прогоните
  `npm --prefix frontend-new run test:e2e:smoke`, посмотрите фактические тела
  запросов, и только потом решайте `strict` или `passthrough`. Для первого
  прохода безопаснее `passthrough` + логирование лишних полей.
- **САМЫЙ ВЕРОЯТНЫЙ СПОСОБ УРОНИТЬ ПРОД ЭТОЙ ЗАДАЧЕЙ — валидация query.**
  `frontend-new/src/services/api.service.ts` в `buildUrl` **автоматически
  подмешивает `groupId` в query каждого запроса**. При этом готового
  query-примитива в `validation.ts` нет (`validateWithSchema` — только тело), то
  есть middleware для query придётся писать с нуля. Если кто-то напишет строгую
  query-схему по образцу body-схемы, **400 полетит одновременно на всех
  endpoint'ах**. Первая query-схема обязана допускать `groupId`, и первый
  прогон — на `passthrough`, не на `strict`.
- **Коды ошибок сначала разойдутся сильнее.** Существующие кирпичи отвечают
  по-разному: `validateIdParam` → `INVALID_ID`, `validateWithSchema` →
  (см. `validation.ts:275+`, там `'Validation failed'`). Фронт ветвится по
  `code` (`frontend-new/src/lib/apiError.ts`, `authRetry.ts`). Значит **словарь
  кодов из задачи 03 нужен ДО контрактных тестов этой задачи** — иначе тесты
  закрепят код, который потом придётся менять, и правка кода станет
  «ломающей тесты», то есть отложится навсегда. В графе зависимостей README
  это учтено: 03 стоит перед 02 по этому пункту.
- **Идемпотентность — два разных риска.**
  `backend/src/api/middleware/idempotency.ts` подключён в 10 route-файлах и
  читает тело до контроллера. Во-первых, порядок: валидация должна стоять
  **после** идемпотентности, иначе ключ считается по невалидированному телу и
  повтор с другим телом попадёт в тот же слот. Во-вторых и важнее: middleware
  **кэширует ответ**. После введения валидации по уже существующим ключам
  начнут отдаваться закэшированные `200` там, где теперь должен быть `400` (и
  наоборот, закэшированные `400` — там, где запрос стал валиден). **Сбросить
  кэш идемпотентности при релизе** — обязательный пункт плана выката, иначе
  на проде будут «необъяснимые» ответы в течение TTL.
- **Формат ошибки.** `validation.ts` сейчас отдаёт `success: false` (13 сайтов).
  Не меняйте формат в этой задаче — это задача 03. Иначе два рефакторинга
  наложатся и разбор регрессии станет невозможным.
- **BigInt в params.** `telegramId` в некоторых роутах — строка с числом,
  превышающим `Number.MAX_SAFE_INTEGER`. `z.coerce.number()` там молча
  испортит значение. Для таких полей нужен `z.string().regex(/^\d+$/)`.
