# 03 — Два контракта ошибок: 430 ручных `success: false` против неиспользуемого `problem.ts`

> **Задача сознательно урезана.** Первая редакция предлагала завести 5 хелперов
> и механически заменить все 430 сайтов в 27 файлах — **без изменения формата
> на проводе**. То есть три дня работы ради «в будущем будет проще добавить
> поле», которого никто не просил. Осталось только то, что даёт эффект сразу:
> единый словарь кодов и перевод `catch`-блоков на `next(err)` (это снимает по
> 5–8 строк с каждого handler'а, чего и хотят задачи 05 и 08). Массовая замена
> ответов — **не делаем**.

- **Приоритет:** P1
- **Оценка:** 0.5 дня
- **Тип:** дублирование контракта
- **Область:** `backend/src/api/**`, `backend/src/utils/problem.ts`, `frontend-new/src/lib/apiError.ts`
- **Метод:** TDD (тест на форму ответа и на конкретный статус)
- **Порядок:** словарь кодов нужен **до** контрактных тестов задачи 02 —
  иначе те тесты закрепят коды, которые потом придётся менять

## Что не так

В репозитории живут **два** формата ошибок:

1. `backend/src/utils/problem.ts` — RFC 7807 (`application/problem+json`), с
   намеренно сохранёнными legacy-зеркалами `success: false` и `error` для
   совместимости с фронтом. Импортируется **ровно одним** файлом —
   `backend/src/api/middleware/error-handler.ts`.
2. Рукописный `res.status(...).json({ success: false, error, code })` — **430
   вхождений в `backend/src/api`** (473 по всему `backend/src`, 450 без тестов):

| Файл | Вхождений |
|---|---|
| `api/controllers/poll.controller.ts` | 91 |
| `api/controllers/category-order.controller.ts` | 53 |
| `api/controllers/admin.controller.ts` | 42 |
| `api/controllers/recurring-poll.controller.ts` | 29 |
| `api/controllers/season.controller.ts` | 23 |
| `api/middleware/telegram-auth.ts` | 22 |
| `api/controllers/menu-suggestion.controller.ts` | 21 |
| `api/controllers/menu.controller.ts` | 19 |
| `api/controllers/user.controller.ts` | 18 |
| `api/controllers/vote.controller.ts` | 16 |
| `api/controllers/auth.controller.ts` | 15 |
| `api/middleware/validation.ts` | 13 |
| `api/controllers/notification.controller.ts` | 13 |
| ещё 14 файлов | 1–8 каждый |

То есть централизованный обработчик ошибок и его формат существуют, но 430 мест
до него не доходят: они отвечают сами, минуя `error-handler`. Отсюда:

- клиент видит две разные формы для одного класса сбоя (одна с
  `type`/`title`/`status`, другая без);
- добавить в ошибки поле (`traceId`, `requestId`) нельзя в одном месте —
  придётся правкой 430 сайтов (именно поэтому этот аргумент и **не** взят в
  объём задачи: такой правки никто не просил);
- коды не нормализованы: `FORBIDDEN`, `ACCESS_DENIED`, `NOT_GROUP_ADMIN` для
  одной ситуации.

**Важно:** `frontend-new/src/services/api.service.ts::toApiError` уже
нормализует любую форму в `{ success: false, error, code, status }`. Значит
фронт не сломается от перехода на problem+json — при условии, что legacy-поля
`success`/`error`/`code` в теле остаются. Тест
`backend/src/__tests__/unit/middleware/error-handler.test.ts:100` («legacy-поля
success и error продолжают приходить») это фиксирует — **его нельзя ломать**.

## Что делать

Ровно два пункта:

1. **Словарь кодов в одном месте** (`ApiErrorCode`-union), чтобы `FORBIDDEN`
   vs `ACCESS_DENIED` vs `NOT_GROUP_ADMIN` перестали расходиться. Существующие
   коды собрать grep'ом, синонимы свести, тип использовать в подписи хелперов
   и в тестах. Это дешёво и сразу окупается в задачах 02, 04, 05, 08.
2. **`catch` → `next(err)`.** Для сайтов внутри `catch`-блоков (это большинство
   `res.status(500)`) — передавать в `error-handler` вместо ручного ответа.
   Убирает по 5–8 строк с каждого handler'а и делает 500-е единообразными.
   Требует, чтобы сервисные ошибки были типизированы (см. риск ниже).

**Что НЕ делать:** заводить набор хелперов `unauthorized/forbidden/badRequest`
и механически переписывать 430 сайтов; переводить фронт на `problem+json`;
удалять legacy-зеркала; менять статус-коды. Первое — работа без адресата,
остальное — см. `tech_debt/STAGE-2-hard.md` (S4), где предварительный вердикт
«не делать».

## TDD-порядок

Один снимок формы на каждый класс ошибки, до правок:

```ts
it.each([
  ['401', () => request(app).get('/api/polls/active')],                 // без токена
  ['403', () => request(app).get('/api/polls/active').set(authOf(outsider))],
])('форма ответа %s не меняется', async (_, call) => {
  const res = await call();
  expect(res.body).toMatchObject({ success: false });
  expect(typeof res.body.error).toBe('string');
  expect(typeof res.body.code).toBe('string');
});
```

Эти тесты должны быть зелёными **до** и **после** — они защищают форму ответа
от того, что перевод `catch` на `next(err)` её изменит. Но их **недостаточно**:
проверка «есть строка в `error`» не заметит, как 409 превратился в 500. На
каждый переводимый handler нужен ещё тест на **конкретный статус** (см. главный
риск ниже).

## Подводные камни

- **ГЛАВНЫЙ РИСК: статус-коды поменяются.** `problem.ts` импортирует **только**
  `error-handler.ts`. Перевод `catch`-блоков на `next(err)` прогоняет через него
  ~200 ошибок, которые сейчас формируются рукой с осмысленным статусом (409 на
  конфликт, 404 на отсутствие, 400 на плохой вход). `error-handler` умеет
  различать лишь то, что типизировано (`PollAlreadyActiveError`, Zod,
  `ValidationError` по имени) — всё остальное станет **500**. Это регрессия,
  видимая пользователю, и она не отловится тестами, если тесты проверяют только
  «не 200». Порядок: сначала типизировать сервисные ошибки (по образцу
  `PollAlreadyActiveError` в `poll.service.ts:48`), затем переводить `catch`;
  и по каждому переводимому handler'у — тест на **конкретный** статус.
- **`res.headersSent`.** Часть handler'ов отвечает, а затем продолжает
  исполнение (нет `return` после `res.json`). При замене на `next(err)` это
  превратится в `ERR_HTTP_HEADERS_SENT`. Проверяйте наличие `return`.
- **SSE.** `api/controllers/sse.controller.ts` (7 сайтов) держит открытый
  поток; там отвечать обычным JSON после начала стрима нельзя. Этот файл —
  последним и вручную.
- **`telegram-auth.ts` (22 сайта)** — это middleware аутентификации, у него два
  пути (legacy initData и Bearer). Ошибки авторизации фронт различает по `code`
  (`INVALID_TOKEN`, `USER_NOT_ACTIVE`) и на них построена переавторизация в
  `frontend-new/src/lib/authRetry.ts`. **Ни один код здесь менять нельзя.**
  Есть тест `telegram-auth.middleware.test.ts:168,185`, который это фиксирует.
- **Не смешивать с задачей 02.** Валидация и формат ошибок трогают одни и те же
  строки. Делайте последовательно, иначе регрессию не разобрать.

## Критерии готовности

- [ ] Словарь кодов — один union-тип; дубликаты-синонимы устранены; тип
      используется в тестах, так что новый синоним не пройдёт компиляцию.
- [ ] Сервисные ошибки, ранее превращавшиеся в 4xx рукой, типизированы.
- [ ] В переведённых на `next(err)` handler'ах есть тест на конкретный статус
      (не «не 200»).
- [ ] `error-handler.test.ts` и `telegram-auth.middleware.test.ts` не менялись
      и зелёные.
- [ ] Число ручных `res.status(500)` в контроллерах уменьшилось; число
      `success: false` **осталось прежним** — это ожидаемо, массовая замена
      вне объёма задачи.
