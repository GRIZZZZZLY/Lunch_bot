> **Задача сознательно урезана.** Первая редакция предлагала завести 5 хелперов
> и механически заменить все 430 сайтов в 27 файлах — **без изменения формата
> на проводе**. То есть три дня работы ради «в будущем будет проще добавить
> поле», которого никто не просил. Осталось только то, что даёт эффект сразу:
> единый словарь кодов и перевод `catch`-блоков на `next(err)` (это снимает по
> 5–8 строк с каждого handler'а, чего и хотят задачи 05 и 08). Массовая замена
> ответов — **не делаем**.

- **Приоритет:** P1
- **Оценка:** 0.5 дня
- **Тип:** дублирование контракта
- **Область:** `backend/src/api/**`, `backend/src/utils/problem.ts`, `frontend-new/src/lib/apiError.ts`
- **Метод:** TDD (тест на форму ответа и на конкретный статус)
- **Порядок:** словарь кодов нужен **до** контрактных тестов задачи 02 —

## Что не так

В репозитории живут **два** формата ошибок:

1. `backend/src/utils/problem.ts` — RFC 7807 (`application/problem+json`), с
   намеренно сохранёнными legacy-зеркалами `success: false` и `error` для
   совместимости с фронтом. Импортируется **ровно одним** файлом —
   `backend/src/api/middleware/error-handler.ts`.
2. Рукописный `res.status(...).json({ success: false, error, code })` — **430
   вхождений в `backend/src/api`** (473 по всему `backend/src`, 450 без тестов):

| Файл | Вхождений |
|---|---|
| `api/controllers/poll.controller.ts` | 91 |
| `api/controllers/category-order.controller.ts` | 53 |
| `api/controllers/admin.controller.ts` | 42 |
| `api/controllers/recurring-poll.controller.ts` | 29 |
| `api/controllers/season.controller.ts` | 23 |
| `api/middleware/telegram-auth.ts` | 22 |

| `api/middleware/validation.ts` | 13 |
| `api/controllers/notification.controller.ts` | 13 |
| ещё 14 файлов | 1–8 каждый |

То есть централизованный обработчик ошибок и его формат существуют, но 430 мест
до него не доходят: они отвечают сами, минуя `error-handler`. Отсюда:

- клиент видит две разные формы для одного класса сбоя (одна с
  `type`/`title`/`status`, другая без);
- добавить в ошибки поле (`traceId`, `requestId`) нельзя в одном месте —
  придётся правкой 430 сайтов (именно поэтому этот аргумент и **не** взят в
  объём задачи: такой правки никто не просил);
- коды не нормализованы: `FORBIDDEN`, `ACCESS_DENIED`, `NOT_GROUP_ADMIN` для
  одной ситуации.

**Важно:** `frontend-new/src/services/api.service.ts::toApiError` уже
нормализует любую форму в `{ success: false, error, code, status }`. Значит
фронт не сломается от перехода на problem+json — при условии, что legacy-поля
`success`/`error`/`code` в теле остаются. Тест
`backend/src/__tests__/unit/middleware/error-handler.test.ts:100` («legacy-поля
success и error продолжают приходить») это фиксирует — **его нельзя ломать**.

## Что делать

Ровно два пункта:

1. **Словарь кодов в одном месте** (`ApiErrorCode`-union), чтобы `FORBIDDEN`
   vs `ACCESS_DENIED` vs `NOT_GROUP_ADMIN` перестали расходиться. Существующие
   коды собрать grep'ом, синонимы свести, тип использовать в подписи хелперов
   и в тестах. Это дешёво и сразу окупается в задачах 02, 04, 05, 08.
2. **`catch` → `next(err)`.** Для сайтов внутри `catch`-блоков (это большинство
   `res.status(500)`) — передавать в `error-handler` вместо ручного ответа.
   Убирает по 5–8 строк с каждого handler'а и делает 500-е единообразными.
   Требует, чтобы сервисные ошибки были типизированы (см. риск ниже).

**Что НЕ делать:** заводить набор хелперов `unauthorized/forbidden/badRequest`
и механически переписывать 430 сайтов; переводить фронт на `problem+json`;
удалять legacy-зеркала; менять статус-коды. Первое — работа без адресата,
остальное — см. `tech_debt/STAGE-2-hard.md` (S4), где предварительный вердикт
«не делать».

## TDD-порядок

Один снимок формы на каждый класс ошибки, до правок:

```ts
it.each([
  ['401', () => request(app).get('/api/polls/active')],                 // без токена
  ['403', () => request(app).get('/api/polls/active').set(authOf(outsider))],
])('форма ответа %s не меняется', async (_, call) => {
  const res = await call();
  expect(res.body).toMatchObject({ success: false });
  expect(typeof res.body.error).toBe('string');
  expect(typeof res.body.code).toBe('string');
});
```

Эти тесты должны быть зелёными **до** и **после** — они защищают форму ответа
от того, что перевод `catch` на `next(err)` её изменит. Но их **недостаточно**:
проверка «есть строка в `error`» не заметит, как 409 превратился в 500. На
каждый переводимый handler нужен ещё тест на **конкретный статус** (см. главный
риск ниже).

## Подводные камни

- **ГЛАВНЫЙ РИСК: статус-коды поменяются.** `problem.ts` импортирует **только**
  `error-handler.ts`. Перевод `catch`-блоков на `next(err)` прогоняет через него
  ~200 ошибок, которые сейчас формируются рукой с осмысленным статусом (409 на
  конфликт, 404 на отсутствие, 400 на плохой вход). `error-handler` умеет
  различать лишь то, что типизировано (`PollAlreadyActiveError`, Zod,
  `ValidationError` по имени) — всё остальное станет **500**. Это регрессия,
  видимая пользователю, и она не отловится тестами, если тесты проверяют только
  «не 200». Порядок: сначала типизировать сервисные ошибки (по образцу
  `PollAlreadyActiveError` в `poll.service.ts:48`), затем переводить `catch`;
  и по каждому переводимому handler'у — тест на **конкретный** статус.
- **`res.headersSent`.** Часть handler'ов отвечает, а затем продолжает
  исполнение (нет `return` после `res.json`). При замене на `next(err)` это
  превратится в `ERR_HTTP_HEADERS_SENT`. Проверяйте наличие `return`.
- **SSE.** `api/controllers/sse.controller.ts` (7 сайтов) держит открытый
  поток; там отвечать обычным JSON после начала стрима нельзя. Этот файл —
  последним и вручную.
- **`telegram-auth.ts` (22 сайта)** — это middleware аутентификации, у него два
  пути (legacy initData и Bearer). Ошибки авторизации фронт различает по `code`
  (`INVALID_TOKEN`, `USER_NOT_ACTIVE`) и на них построена переавторизация в
  `frontend-new/src/lib/authRetry.ts`. **Ни один код здесь менять нельзя.**
  Есть тест `telegram-auth.middleware.test.ts:168,185`, который это фиксирует.
- **Не смешивать с задачей 02.** Валидация и формат ошибок трогают одни и те же
  строки. Делайте последовательно, иначе регрессию не разобрать.

## Что выяснилось при исполнении

### Главная находка: почти половина кодов не имела текста для пользователя

Словарь текстов на клиенте (`frontend-new/src/lib/apiError.ts`) существовал и
покрывал 45 кодов. Остальные **молча падали в запасной текст**: сервер называл
причину, а пользователь читал «не удалось».

**Код попадает в ответ ТРЕМЯ способами, и первые замеры видели только один.**
Это стоило одной внесённой и снятой ошибки, поэтому стоит записать все три:

1. Литералом в контроллере — `code: 'INVALID_ID'`. Их находит `grep`, их 89.
2. Конструктором класса из `utils/error.ts` — `error-handler` отдаёт `code`
   любого `BaseError` как есть. `grep "code:"` их НЕ находит. И это не теория:
   `AuthorizationError` бросается из `cors.ts`, то есть `AUTHORIZATION_ERROR`
   доходил до клиента уже сегодня, без текста.
3. Через **union-тип сервисного класса** — `StoreRunError`, `GroupAccessError`:
   контроллер пишет `code: err.code`, а список значений живёт в подписи
   конструктора. Тоже невидимо для `grep`.

На третьем способе я и ошибся: счёл `INVALID_INPUT` мёртвым кодом и снял у него
текст — а `store-run.controller` отдаёт его клиенту как 400 из девяти мест в
сервисе. Ревью это поймало. Теперь тест собирает коды всеми тремя способами
и дополнительно проверяет, что каждый сборщик вообще что-то нашёл: пустое
множество проходит любой `filter`, то есть поломка обхода сделала бы тесты
вакуумными.

Итог: **92 кода в 9 группах**, у каждого есть текст, и это проверяется.

### Попытка свести синонимы иерархии — сделана и откачена

Первым проходом коды классов были сведены к каноническим
(`AUTHENTICATION_ERROR`→`UNAUTHORIZED` и т. д.). Это выглядело безопасным:
на тот момент ни один сервис этих классов не бросал. **Тесты показали, что нет:**
11 падений, включая `error-handler.test.ts`, который задача велит не менять.
И `AuthorizationError` из `cors.ts` действительно уходит клиенту, то есть
переименование — смена контракта.

Откачено. Пробел закрыт **текстами**, а не переименованием: у пользователя
появилась причина, форма ответа не изменилась. Сведение синонимов оставлено как
отдельное решение — его надо делать вместе с фронтом, а не мимоходом.

### Пункт 2 (`catch → next(err)`) сделан на одном файле из десяти

Замер: **73** catch-блока отдают ровно `500 INTERNAL_ERROR`. Ещё **68** несут
осмысленный статус (409, 404, 400) и требуют сначала типизации сервисных
ошибок, как и предупреждает раздел риска.

**Поправка к моему же обоснованию.** Я написал, что перевод таких блоков
«статус изменить не может». Это неверно, и нашло это ревью:
`error-handler` распознаёт известные ошибки Prisma — `P2002` → 409
`DUPLICATE_ENTRY`, `P2025` → 404 `NOT_FOUND`, — то есть у переведённых
handler'ов сбой БД теперь даёт не 500. Для продукта это лучше, но менять
контракт молча нельзя: оба случая закреплены тестами
(`category-order-error-delegation.test.ts`), включая «неизвестный код Prisma
остаётся 500».

Переведён `category-order.controller.ts` — 11 блоков, тот файл, который режет
задача 08. Почему один, а не все 73: перевод меняет подпись handler'а на
`(req, res, next)`, а тесты вызывают handler'ы напрямую двумя аргументами.
На один файл это 64 вызова и 12 утверждений; на все — около 400, и каждое
меняет смысл (тест перестаёт проверять ответ и начинает проверять делегирование).
Делать это одним махом без пофайловой проверки — тот самый способ получить
«что-то стало 500».

Рецепт для остальных 62 блоков зафиксирован: `mockNext()` в
`__tests__/helpers/http.ts`, скрипт-переводчик берёт только блоки с ровно
`500 INTERNAL_ERROR`, и на каждый файл — тест композиции
(`category-order-error-delegation.test.ts`), который прогоняет handler через
настоящий `errorHandler` и проверяет КОНКРЕТНЫЙ статус. Именно этот тест поймал,
что общая замена задела `finalizeCalculation` с его собственным кодом
`FINALIZATION_ERROR`.

## Критерии готовности

- [x] Словарь кодов — один union-тип (`backend/src/api/error-codes.ts`),
      **92 кода в 9 группах**. Тип применён в продакшене, а не только в тесте:
      `Problem.code` и `makeProblem`/`respondProblem` в `utils/problem.ts`
      принимают `ApiErrorCode`, поэтому опечатка в литерале больше не
      компилируется. Применение типа сразу нашло два места, передававших
      `string`: `BaseError.code` (сужен через `isApiErrorCode`, неизвестный код
      заменяется на `INTERNAL_ERROR` — у него текст есть) и `respondProblem`.
- [x] Тест сверяет union со ВСЕМИ тремя способами доставки кода (литералы,
      классы `utils/error.ts`, union-типы сервисных ошибок) и со словарём
      текстов фронта; плюс проверяет, что каждый сборщик что-то нашёл.
- [x] Синонимы устранены там, где это НЕ меняет контракт: `INVALID_REQUEST`,
      `INVALID_BODY`, `INVALID_PARAMS` → `VALIDATION_ERROR` (фронт давал всем
      трём один и тот же текст, то есть для пользователя ничего не изменилось).
      Таблица `RETIRED_CODE_ALIASES` + тест не дают им вернуться.
      `INVALID_REQUEST_BODY` оставлен: это «тело не разобралось», другой смысл,
      и он закреплён защищённым тестом.
- [ ] **НЕ СДЕЛАНО: типизация сервисных ошибок.** Иерархия
      (`ValidationError`, `NotFoundError`, `ConflictError`, …) существует и
      **её не бросает ни один сервис** — 0 использований. Это предпосылка для
      остальных 68 catch-блоков, и она пересекается с задачами 05–08, которые
      будут переписывать те же сервисы. Делать её надо там.
- [x] В переведённых handler'ах есть тест на конкретный статус:
      `category-order-error-delegation.test.ts` соединяет handler с настоящим
      `errorHandler` и проверяет 500/404/400 и legacy-поля, а не «не 200».
- [x] `error-handler.test.ts` и `telegram-auth.middleware.test.ts` **не
      менялись** (`git diff` по ним пуст) и зелёные.
- [x] Ручных `res.status(500)` в `category-order.controller.ts` было 12,
      осталось **1** (`FINALIZATION_ERROR`, у него свой код).
- [ ] **Критерий про `success: false` не выполнен, и формулировка была
      неверной.** В `category-order.controller.ts` было 42, стало 31 — минус 11,
      ровно столько, сколько catch-блоков переведено. Это неизбежное следствие
      пункта 2: ответ теперь формирует `errorHandler`, и `success: false`
      появляется там, а не в контроллере. Критерий имел в виду «не делать
      массовую замену ответов», и она не сделана; но записан он был как «число
      не изменится», что при переводе `catch` невозможно.

### Ещё правки по итогам ревью

- Три текста описывали не ту ситуацию, что отдаёт сервер, и исправлены по
  сайту-источнику: `SECURITY_VIOLATION` (сервер отвечает 500 «Server
  misconfiguration» — это не отказ по безопасности), `INVALID_QUERY` (это
  «поиск от 2 символов», единственная ошибка из списка, которую пользователь
  может исправить сам), `ALREADY_COMPLETED` (источник только голосование).
- **Тексты для ограничителей частоты перекрывали серверные.** `apiError.ts`
  сверяется со словарём ДО русского `message` с сервера, а лимитеры присылают
  туда конкретное время ожидания («Подождите час»). Словарная фраза «подождите
  немного» заставила бы повторить сразу и снова упереться. Введён явный набор
  `SERVER_TEXT_WINS`: для этих кодов серверный текст проверяется первым, а
  запись в словаре остаётся подстраховкой.
- `INVALID_REQUEST_BODY` — единственный код, у которого текст УЖЕ был; я его
  переписал без нужды. Возвращён исходный.
- Добавлены тесты фронта на словарь (`lib/__tests__/apiError.test.ts`): их не
  было ни на одну из новых записей. Проверяются не все 93, а те, где легко
  ошибиться: приоритет серверного текста у лимитеров и коды, приходящие через
  классы ошибок, а не литералом.

## Дважды защищённый тест остановил переусложнение

`error-handler.test.ts` задача велит не менять — и он дважды поймал попытку
сделать контракт «аккуратнее», чем он есть:

1. Переименование кодов иерархии в канонические — 11 падений. Откачено.
2. Сужение `code` до `ApiErrorCode` в самом обработчике: тест «наследник
   BaseError с чужим кодом сохраняет его» показал, что `BaseError` **открыт для
   наследования** намеренно, и подменять неизвестный код на `INTERNAL_ERROR`
   значит ломать заявленное свойство. Осталось одно приведение типа в этом
   месте, с объяснением почему; гарантию там даёт не тип, а тест словаря,
   который собирает коды из классов и требует для каждого текст.

Вывод, полезный за пределами задачи: тест, который что-то запрещает, ценнее
аккуратности, которую он запрещает. Оба раза «правильнее» означало «меняет
контракт».
