# 04 — Матрица авторизации (шаг 0 задачи [04](04-authorization-layer.md))

Составлено 2026-08-23 машинным обходом `backend/src/api/routes/*.ts` и
`backend/src/api/controllers/*.ts`: скрипт разбирает каждый `router.<method>(`
по балансировке скобок, собирает цепочку middleware (включая `router.use`) и
ищет в теле handler'а известные проверки доступа.

Матрица — не бюрократия. Задача 04 переносит проверки на маршрут, а это меняет
**момент** проверки. Три теста на 403 такого не покажут; ниже три места, где
наивный перенос открыл бы эндпоинт шире или сломал бы валидацию.

## Покрытие

| Показатель | Значение |
|---|---|
| Эндпоинтов всего | **153** |
| Под middleware на маршруте | 144 |
| Публичных по замыслу | 4 — `POST /api/auth/validate` (вход) и три `GET /api/health/*` |
| Только dev | 5 — `GET /api/test/*`, смонтированы под `NODE_ENV !== 'production'` (`server.ts:204`) |
| Без middleware в проде | **0** |
| **С middleware, но НЕ проверяющим тот ресурс** | **2 — см. Находку 0** |

> **Поправка к первой редакции этой матрицы.** Строка «без проверки в проде: 0»
> была верной и при этом вводила в заблуждение: она считала НАЛИЧИЕ middleware,
> а не то, ту ли сущность он проверяет. Внешнее ревью на это указало, проверка
> подтвердила две настоящие утечки. Мера «эндпоинтов без middleware» для
> авторизации недостаточна — нужна мера «middleware проверяет тот же ресурс,
> которым распоряжается handler».

## Находка 0 — `requireGroupAdmin` не связывает группу с ресурсом (2 утечки)

`api/middleware/group-admin.ts` берёт `groupId` из `params` → `query` → `body`
и проверяет, что вызывающий администрирует ЭТУ группу. Связи с ресурсом,
которым распоряжается handler, нет никакой. Значит достаточно быть админом
своей группы и прислать чужой id ресурса вместе со своим `groupId`.

**Утечка 1 — история правок чужой группы.**
`GET /api/order-items/:id/edit-history` →
`OrderCalculationService.getEditHistory(orderItemId)` фильтрует только по
`orderItemId`. Админ группы A: `GET /api/order-items/<позиция группы B>/edit-history?groupId=A`
→ проходит → получает историю правок группы B.
**Исправлено:** `requireOrderItemGroupAdmin` выводит группу из самой позиции
(позиция → категорийный заказ → опрос → группа). Подделать нечем.

**Утечка 2 — статистика любого пользователя.**
`GET /api/polls/user-stats/:userId` →
`PollService.getUserParticipationStats(userId)` для ЛЮБОГО `userId`. Комментарий
на маршруте утверждал «статистика чужого человека — данные его группы», но
принадлежность человека к этой группе не проверял никто.
**Исправлено:** `requireGroupAdminOverUser` требует ДВА условия — вызывающий
администрирует группу И целевой пользователь в ней состоит. Оба отказа отвечают
одинаково: разные ответы позволяли бы перебором выяснять состав чужой группы.

**Где `requireGroupAdmin` остаётся и почему это безопасно.** Проверено по
каждому: `menu.routes.ts` (4 маршрута) — `MenuService.updateMenuItem` сам
достаёт `groupId` блюда и вызывает `GroupService.assertAdmin` по нему;
`menu-suggestion.routes.ts` (4) — `assertSuggestionGroup` бросает, если
`suggestion.groupId !== groupId`. То есть там ресурс со группой связывает
СЕРВИС. Это работает, но полагается на то, что каждый следующий handler не
забудет сделать то же самое.

**Вывод для остальных задач каталога:** `requireGroupAdmin` безопасен только в
паре с проверкой в сервисе. Новый маршрут под ним без такой проверки — утечка
по умолчанию.

Отдельно проверено: `GET /api/avatar/:fileId` защищён не токеном, а
HMAC-подписью URL (`avatarAccessMiddleware`) — `<img src>` не может нести
заголовок `Authorization`. Это осознанное решение с TTL 24 ч, а не пропуск.

## Находка 1 — в `saveOrderItem` две проверки про РАЗНЫХ людей

`category-order.controller.ts:325` и `:338`, один handler:

```ts
if (responsibleUserId !== user.id)                    // 403: кто ЗВОНИТ
if (!isUserParticipant(categoryOrderId, parsedUserId)) // 403: кого УКАЗАЛИ в body
```

Первая — авторизация вызывающего, переносится на маршрут. Вторая — **проверка
полезной нагрузки**: «позицию можно создать только участнику категории», и
`parsedUserId` приходит из тела запроса. Перенос второй в middleware
бессмыслен (в middleware нет разобранного body) и опасен: правило исчезнет, а
выглядеть будет как «перенесли».

**Вывод:** в middleware уходит только первая. Вторая остаётся в handler'е, и
это надо написать в комментарии, иначе следующий «доперенесёт».

## Находка 2 — одно правило записано двумя способами

| Строка | Условие |
|---|---|
| `:234` | `responsibleUserId !== user.id && !isParticipant` |
| `:485` | `!isResponsible && !isParticipant` |

Это одно и то же правило «ответственный ИЛИ участник», но во втором месте
`isResponsible` вычисляется отдельно. При переносе они должны стать **одним**
middleware; сейчас достаточно поправить одно место, чтобы правила разошлись.

## Находка 3 — 403 в ответ на отсутствие аутентификации

`category-order.controller.ts:870` отвечает `403 FORBIDDEN` с текстом
«Admin access required» на условие `if (!user)` — то есть на отсутствие
аутентификации. Авторизацию там действительно делает `groupAdminMiddleware` на
маршруте, и комментарий выше это честно объясняет; но остаток проверки
отвечает не тем кодом.

**Не исправляется в задаче 04** — задача прямо запрещает менять коды и статусы
(это предмет задачи [03](03-single-error-contract.md)). Занесено туда.

## Различные предикаты авторизации в `category-order.controller.ts`

| Предикат | Сайтов | Куда переносится |
|---|---|---|
| `!canAccessPoll(pollId, user)` | 3 (`:104`, `:156`, `:685`) | `requirePollAccess` |
| `responsibleUserId !== user.id` | 6 (`:325`, `:419`, `:546`, `:620`, `:777`, `:931`) | `requireCategoryOrderResponsible` |
| `responsible ИЛИ участник` | 2 (`:234`, `:485`) | `requireCategoryOrderParticipant` |
| `!isParticipant(…, parsedUserId)` | 1 (`:338`) | **остаётся в handler'е** (Находка 1) |
| `!user` → 403 | 1 (`:870`) | остаётся, код правит задача 03 |

`canAccessPoll` ходит в Prisma напрямую из контроллера
(`prisma.poll.findUnique` + `prisma.groupMember.findUnique`) — то есть правило
«участник активной группы этого опроса» описано в HTTP-слое. В
`GroupService.isUserGroupMember` то же правило уже есть, и `poll.controller`
пользуется именно им. То есть правило существует в двух реализациях, и
проверка на `isActive` в одной из них может разойтись с другой.

## Пять форм ответа на «ты не авторизован»

Замерено после закрытия пункта 10.1: рядом с 34 вызовами общего
`requireAuthUser` живут 34 рукописных проверки, и отвечают они по-разному.

| Форма | Где |
|---|---|
| `401` + `UNAUTHORIZED` (+`timestamp`) | `middleware/require-auth-user.ts` |
| `401` + `UNAUTHORIZED` | 8 сайтов |
| `401` + `NOT_AUTHENTICATED` | 7 сайтов, `user.controller.ts:64,105,139,213` |
| `403` без кода | `gamification.controller.ts:222,277`, `season.controller.ts:226,268` |
| `400` | `gamification.controller.ts:284`, `group-admin.ts:21` |
| тело без поля `success` | `budget.controller.ts` |

Фронт ветвится по `code`. Единый код должен прийти из словаря задачи 03 —
поэтому задача 04 сводит проверки в одно место, а форму ответа не меняет.

## Как воспроизвести

Скрипт-обходчик лежит в скратчпаде сессии, а не в репозитории: он одноразовый и
проверяет то, что после задачи 04 перестанет быть правдой. Если понадобится
снова — он извлекает `router.<method>(` по балансировке скобок (регулярка на
одну строку теряет многострочные цепочки: первая версия нашла 130 эндпоинтов
из 153) и ищет в теле handler'а список известных проверок. Тела вида
`export const x = async (…) =>` надо разбирать отдельно от `async x(…)` —
шесть handler'ов `recurring-poll` иначе не находятся.
