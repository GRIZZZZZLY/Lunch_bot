## Из чего состоят эти строки (и почему они уйдут почти сами)

Каждый handler — это последовательность:

1. `getAuthUser` + `requireGroupMember`/`requireGroupAdmin` → **уходит в задачу 04**;
2. `parseInt` / `isNaN` / разбор `req.body` → **уходит в задачу 02**;
3. 3–5 повторяющихся блоков `res.status(...).json({ success: false, ... })` → частично уходит в задачу 03 (там осталась только замена `catch` на `next(err)` — массовая замена ответов признана работой без адресата);
4. **бизнес-сценарий** — вот это и есть предмет данной задачи;
5. `try/catch` с `logger.error` + `res.status(500)` → заменяется на `next(err)`.

**Поэтому порядок важен:** сделайте 02, 03, 04 — и файл усохнет
без риска, чисто механически. Только после этого берите шаг 4.

## Что делать с шагом 4

Перенести сценарии в сервисный слой, оставив в контроллере: разбор уже
провалидированного запроса → вызов одного метода сервиса → сериализация ответа.

Конкретно:

- `createPollFromWebApp` (185) — уже есть `poll.service.extensions.createPollFromWebApp`.
  Контроллер дублирует его обвязку. Свести к одному вызову; вся работа с
  ботом/клавиатурами остаётся в сервисе.
- `voteMultiple` (154) и `vote` (111) — общая часть (проверка активности опроса,
  лимита `maxSelections`, идемпотентности) вынести в `VoteService`;
  `vote` становится частным случаем `voteMultiple` с одним элементом.
- `completePollMultiWinner` (132) — целиком делегировать
  `PollService.completePollMultiWinner` (см. задачу 06).
- `repeatPoll` (99) — сценарий «взять последний завершённый опрос и создать
  такой же» принадлежит сервису.

## TDD-порядок

Перенос логики без тестов на неё — это переписывание. Поэтому:

1. **Характеризующий тест до правки** на каждый переносимый handler: запрос →
   ожидаемый статус и форма тела. Не «как должно быть», а **как есть сейчас**,
   включая странности. Это фиксация текущего контракта.
2. Перенос в сервис. Тесты уровня HTTP остаются зелёными без изменений — это
   и есть доказательство, что перенос не изменил поведение.
3. Новые unit-тесты уже на сервисный метод (они дешевле и быстрее HTTP-тестов).
4. Только после этого — упрощение логики, если оно нужно.

Существующее покрытие backend высокое (94% statements по замеру в CI), так что
часть характеризующих тестов уже есть — **сначала посмотрите, что уже покрыто**
в `backend/src/__tests__/unit/controllers/`, не дублируйте.

## Подводные камни

- **Упадёт `functions: 89`, а не `statements: 94`.** `backend/jest.config.js`
  держит четыре порога (`branches: 88`, `functions: 89`, `lines: 94`,
  `statements: 94`). Extract-method плодит **функции** быстрее, чем строки:
  каждая извлечённая функция — новый знаменатель для `functions`, и если её
  ветки не покрыты, первым красным станет именно этот порог. Смотрите на него,
  а не только на `statements`. Понижать пороги нельзя — в комментарии к конфигу
  описано, чем закончилось прошлое понижение.
- **`serializeBigInt`.** Контроллер вызывает `serializeBigInt` перед ответом
  (`telegramId` — BigInt в Prisma). При переносе логики в сервис не тащите
  сериализацию в сервис: она относится к транспорту. Иначе сервис начнёт
  возвращать строки там, где вызывающему нужны числа.
- **`PollAlreadyActiveError`.** Сервис уже бросает типизированную ошибку с
  `code = 'POLL_ALREADY_ACTIVE'`, а контроллер её ловит и переводит в 409.
  Это правильный шаблон — расширяйте его, а не заводите второй способ.
- **SSE-инвалидация.** Часть handler'ов после мутации публикует событие в
  `event-bus.service`. При переносе легко потерять публикацию — и фронт
  перестанет обновляться живьём, а тесты этого не увидят (у `event-bus.service`
  **нет ни одного теста** — он второй в приоритетной четвёрке задачи **11**).
  Перед переносом добавьте тест «мутация → событие опубликовано».
- **Не делать это одним коммитом.** 1746 строк одним диффом никто не
  отревьюит, и bisect по регрессии станет бесполезен.

## Что выяснилось при исполнении

### Порядок задач сработал, но не так, как обещал план

План говорил: сделайте 02, 03, 04 — и файл «усохнет сам, механически». Замер:
1746 → 1499 строк, то есть **247**, а не обещанные ~330. Валидация действительно
ушла целиком, но `catch`-блоки — нет: задача 03 сознательно оставила их до
типизации сервисных ошибок и передала эту предпосылку сюда. Остальные 850 строк
пришлось разбирать руками, и это и была работа.

### Что куда уехало

| Откуда | Куда | Почему туда |
|---|---|---|
| `createPollFromWebApp` (173 строки в контроллере), `repeatPoll` (88) | `services/poll-creation.service.ts` | Это не адаптер HTTP: проверить группу → проверить активное голосование → собрать блюда → создать → отправить сообщение в Telegram. Контроллер знал порядок пяти вызовов сервисов. Новый файл, а не `poll.service.ts`: его режет задача 06, дописывать в него — идти против следующей задачи |
| Правила выбора (`isMultiSelect`, `maxSelections`) | `VoteService.castVotes` | Предел считался в контроллере, то есть действовал ровно для одного эндпоинта. Заодно голосование читается `select` из двух полей вместо объекта с голосами и пользователями |
| `requireGroupMember` / `requireGroupAdmin` / `getAccessibleGroupIds` | `api/access/poll-access.ts` | Возвращали `boolean`, и после каждого вызова нужен был `if (!hasAccess) return;` — две строки, в которых легко забыть `return` и продолжить исполнение после отправленного ответа. Теперь бросают |
| Расчёт `endTime`, фильтр голосов по составу, разбор `rouletteData` | `api/controllers/poll.view.ts` | Форма ответа — транспорт, и нужна она клиенту, а не планировщику. Каждая функция вызывается из двух handler'ов |
| Доменные ошибки (`Poll not found`, `Only an active poll can be cancelled`, …) | `services/poll.errors.ts`, `services/vote.errors.ts` | Предпосылка из задачи 03. Статус и код несёт класс, а не совпадение строки в `catch` |

Ни один handler больше не отвечает об ошибке: **Express 5** передаёт отказ
асинхронного обработчика в цепочку ошибок сам. `catch` в файле осталось два, и
оба не про ответ: один гасит сбой автозавершения (голос уже записан, закрытие
голосования — отдельное следствие), второй переводит код ошибки в исторический
для одного эндпоинта. Это и есть причина, по которой
`try/catch` + `next(err)` (как в задаче 08) здесь не понадобился — но полагаться
на это молча нельзя, поэтому есть
`__tests__/unit/controllers/poll-error-delegation.test.ts`: настоящее приложение
и настоящий HTTP-запрос. Сломанная передача выглядит как **повисший запрос**, а
не как неверный статус, и ни один тест с моками этого не увидит.

### Два дефекта, найденных по дороге

1. **`error-handler` подменял код у любой нашей ошибки с 400.** Проверка «это
   сбой разбора тела от body-parser» смотрела на `err.status`/`err.statusCode`,
   а `BaseError` несёт `statusCode` сам — и первая же типизированная 400-я из
   контроллера получила `INVALID_REQUEST_BODY` вместо своего кода. Пока
   контроллеры отвечали 400 сами, до этой ветки такие ошибки не доходили.
2. **`BotNotInitializedError` был обычным `Error`.** Ветка 503 работала только
   потому, что контроллер узнавал тип; после переноса сценария в сервис она бы
   умерла молча. Класс теперь несёт 503 `BOT_NOT_AVAILABLE` сам.

Плюс два дефекта, закрытых предыдущим коммитом той же задачи (типизация
ошибок): завершение отменённого голосования отдавало 500 вместо 409, а ветка
400 у снятия голоса была **недостижима** — свой же `catch` подменял причину на
«Failed to remove vote».

### Тесты: 157 вызовов handler'а не пришлось переписывать

Перевод на «handler бросает» ломает любой тест, который вызывает handler двумя
аргументами. Вместо правки 157 вызовов в `helpers/http.ts` добавлен
`withErrorHandler(Controller)`: обёртка подставляет НАСТОЯЩИЙ `errorHandler`, и
существующие утверждения про `res.statusCode` / `res.body` продолжают проверять
то, что увидит клиент. Побочный эффект полезнее самой замены: каждый такой тест
стал тестом делегирования — «409 превратился в 500» падает сразу.

Заодно убран самодельный `PollAlreadyActiveError` из фабрики мока: тест
проверял собственную выдумку, которая разошлась бы с настоящим классом при
первом же его изменении.

### Сколько тестов переехало вслед за кодом

Проверки сценариев (состав блюд, значения по умолчанию, отказы) переехали из
теста контроллера в `poll-creation.service.test.ts` и `vote.service.test.ts` —
там они дешевле: не нужно поднимать запрос, чтобы узнать, что
`maxSelections: 10` превращается в 3. В тесте контроллера на их месте — проверка
делегирования и того, что отказ сервиса доезжает СВОИМ статусом.

## Что осталось

- **Правило «закрыть голосование по кворуму» всё ещё в HTTP-слое.**
  `autoCompleteIfQuorumReached` вызывается после каждого голоса из контроллера и
  дублирует `PollService.checkQuorumAndComplete`, у которой уже есть тесты.
  Перенос — вместе с задачей 06, с замером: два пути закрытия голосования
  (после голоса и по таймеру) должны стать одним.
- **Исторические коды `PATCH /polls/:id/complete-multi`.** Этот эндпоинт
  называет те же ситуации иначе (`NOT_FOUND` вместо `POLL_NOT_FOUND`,
  `ALREADY_COMPLETED` вместо `POLL_ALREADY_COMPLETED`), и у обоих кодов на
  фронте свой текст. Пока код переводится обратно (`withLegacyCode` — одно
  место, с объяснением). Сведение синонимов — отдельное решение вместе с
  фронтом, как и записано в задаче 03.
- **`api/access/poll-access.ts` — временный адрес.** Задача 04 переносит
  авторизацию в middleware маршрута; тогда этот файл станет её внутренностями
  или исчезнет.
