# Этап 2 — задачи, которые надо обсудить до внедрения

Здесь не «остатки», а изменения, у которых **цена сопоставима с выгодой** или
выгода зависит от планов продукта. Каждая описана так, чтобы решение «делаем /
не делаем» можно было принять без повторного исследования.

Ни одну из них не следует начинать до закрытия задач 01–08: они меняют
основания, на которые опираются те правки.

---

## S1. Слой доступа к данным (repository / data-mapper)

**Что.** Сейчас Prisma вызывается напрямую из сервисов (30 файлов), из
контроллеров (`category-order.controller`), из джобов и из скриптов. Слоя
между доменом и ORM нет.

**За.** Правила выборок (`select`, `include`, фильтры активности,
`isActive`-условия) перестанут дублироваться; текущие 390 планов
`dry_violation` в основном именно про это. Тесты сервисов перестанут требовать
живой PostgreSQL — сейчас `globalSetup` поднимает тестовую БД, и это
единственная среда, где считается покрытие (замер делается только в CI).

**Против.** Это самое дорогое изменение в списке: ~30 сервисов, 3488 тестов
завязаны на текущую форму. Prisma сама по себе уже data-mapper; добавление
второго слоя часто даёт «анемичный репозиторий» — обёртку 1:1, которая только
добавляет файл на каждый запрос.

**Что решить.** Нужен ли слой целиком или только для 3–4 доменов с самой
сложной выборкой (`poll`, `vote`, `category-order`, `budget`). Частичное
внедрение честнее: если оно не окупится, отката потребует 4 домена, а не 30.

## S2. Уведомления через события вместо прямых вызовов

**Что.** Сервисы вызывают `NotificationService` напрямую. `poll.service`
импортирует `notification.service`, тот импортирует Prisma и бота — отсюда
циклы, обходимые динамическим `await import` (см. задачу 06).

**За.** Разрывает циклы структурно, а не заплаткой. `event-bus.service.ts`
(140 строк) уже существует и используется для SSE — инфраструктура наполовину
есть. Домен перестаёт знать про Telegram.

**Против.** Асинхронные события ломают текущие гарантии: сейчас
`sendPollCompletionNotifications` вызывается **внутри** сценария завершения,
и если он упал, это видно вызывающему. С шиной событий сбой уведомления
станет невидимым, если не добавить dead-letter/ретраи — а это уже отдельная
инфраструктура.

**Что решить.** Готовы ли принять «уведомление может тихо не уйти» в обмен на
развязку. Возможен промежуточный вариант: события только для того, что уже
и так не критично (геймификация, статистика), прямые вызовы — для того, что
пользователь ждёт (результат опроса, долг).

## S3. Разрезание `bot/bot.ts`

**Что.** 704 строки, max CCN **54** (худшее значение в репозитории), health 2.96,
maintainability 4.6, 11 коммитов за 90 дней.

**Нюанс.** Файл **осознанно исключён из измерения покрытия** — в
`backend/jest.config.js` есть аргументированный комментарий: «710 строк
регистрации хендлеров, команд и middleware, своей логики почти не несёт,
тестируемые части живут отдельными файлами». Аргумент разумный.

**За.** CCN 54 говорит, что «своей логики почти не несёт» — уже не совсем
правда: где-то внутри регистрации выросло ветвление. Стоит посмотреть, что
именно даёт 54.

**Против.** Это точка входа. Ошибка при разрезании = бот не отвечает, и
тестами это не поймается (файл вне покрытия по решению выше). Риск
несоразмерен выгоде, если внутри действительно только регистрация.

**Что решить.** Сначала дешёвая диагностика: найти функцию с CCN 54
(`get_health(targets=["backend/src/bot/bot.ts"], include=["biomarkers"])`).
Если это одна функция с логикой — вынести только её, файл не трогать. Если
ветвление размазано — обсуждать разрезание отдельно.

## S4. Полный переход на RFC 7807 и удаление legacy-полей

**Что.** Задача 03 сохраняет `success`/`error` в теле. Полный переход — это
убрать legacy-зеркала и перевести фронт на `problem+json`.

**За.** Один формат, стандартный, машиночитаемый.

**Против.** Фронт и бэк деплоятся не атомарно. Есть тест
`error-handler.test.ts:100`, специально фиксирующий, что legacy-поля
продолжают приходить — «сломать их значит сломать фронт». Обработка ошибок
разбросана по `frontend-new/src/lib/apiError.ts`, `authRetry.ts` и
`api.service.toApiError`. Выгода — косметическая; цена — синхронный релиз двух
пакетов.

**Что решить.** Скорее «не делать», пока нет внешних потребителей API.
Зафиксировать это решение письменно, чтобы вопрос не поднимался снова.

## S5. Машина состояний для жизненного цикла опроса

**Что.** Статусы опроса (`ACTIVE` → `COMPLETED`/`CANCELLED`, плюс
multi-winner и store-run со своими `COLLECTING`/`SHOPPING`/`SETTLED`) проверяются
условиями в разных местах: `checkQuorumAndComplete`, `checkAutoComplete`,
`cancelExpiredPolls`, `completePoll`, `completePollMultiWinner`,
джобы авто-закрытия.

**За.** Переходы описаны в одном месте, недопустимый переход становится
ошибкой компиляции или явной проверкой, а не «забыли условие в шестом месте».
Существующие комментарии в коде показывают, что гонки здесь уже ловили и
чинили транзакциями — то есть проблема реальная.

**Против.** Сейчас переходы защищены оптимистической блокировкой в `where`
(`{ id, status: 'ACTIVE' }`) — это работает. Явная машина состояний добавит
абстракцию поверх работающего механизма. Выгода проявится, если статусов
станет больше.

**Что решить.** Планируется ли расширение жизненного цикла (например,
«опрос на паузе», «переголосование»). Если нет — не делать.

## S6. Мутационное тестирование backend

**Что.** Покрытие 94% statements / 88% branches — высокое. Но покрытие
показывает, что строка исполнилась, а не что тест бы упал при поломке.

**За.** На таком уровне покрытия мутационное тестирование (Stryker) — почти
единственный способ узнать, какие из 3488 тестов реально что-то проверяют.
Дешёвый способ найти тесты-пустышки.

**Против.** Прогон долгий (3488 тестов × мутанты), требует живой PostgreSQL
(`globalSetup`), в CI не поместится. Придётся запускать вручную или ночным
джобом.

**Предварительная рекомендация — не делать.** Прямо противоречит установке
«минимально достаточные правки для максимального результата в ближайшее время».
Если когда-нибудь возвращаться — только разовый прогон по 5–6 денежным
сервисам (`budget.service`, `order-calculation.service`,
`store-run-budget.service`, `poll.service`, `vote.service`), ~день работы.
Регулярный прогон избыточен при любом раскладе. Достаточно зафиксировать
«не делаем» и закрыть вопрос.

## S7. Разделение фронтенда на слои (feature-sliced)

**Что.** Сейчас в `frontend-new/src` соседствуют `features/`, `components/`,
`pages/`, `lib/`, `shared/`, `services/`, `hooks/`, `store/`. Это два разных
подхода к организации (по типу и по фиче) одновременно: `pages/AdminPage.tsx`
рядом с `features/home/`, `lib/pollMappers.ts` рядом с `shared/lib/pluralize.ts`.

**За.** Одна схема вместо двух; при 137 исходных файлах (206 всего в
`frontend-new/src`, из них 46 тестовых и 23 css) это ощутимо.

**Против.** Массовое перемещение файлов ломает историю git (`git blame`,
`git log --follow` частично), делает бесполезными закладки и ссылки в
документации, и не исправляет ни одного дефекта. Метрики здоровья фронта
приличные (average 8.17 против 7.45 у backend).

**Что решить.** Скорее «нет, но зафиксировать правило для нового кода»: новые
модули — только в `features/<домен>/` и `shared/`, `pages/` и `lib/` не
пополняются. Тогда структура сойдётся сама за несколько месяцев, без большого
диффа.
