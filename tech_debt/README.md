## Порядок работ

Порядок не произвольный.

- **02, 03, 04 — расчистка перед разрезанием.** 60–70% строк в god-файлах
  (задачи 05, 06, 08) — это парсинг входа, авторизация и ручные ответы об
  ошибках. Начав с разрезания, вы будете переносить между модулями тот же
  дублированный код.
- **10.1 идёт перед 04.** Расширение типа Express для `req.user` (84 сайта в
  18 продакшен-файлах) должно быть сделано до переноса `getAuthUser` в
  middleware, иначе перенос придётся типизировать вторым проходом.
- **09.4, затем 14.1 — жёсткие предпосылки 06 и 07.** Битая кодировка
  (28 строк) и дублированная плюрализация живут ровно в тех файлах, которые
  режут 06 и 07; иначе мусор и дубликаты разъедутся по новым модулям. Между
  собой 09.4 и 14.1 **конфликтуют по файлу** `notification.service.ts` —
  строго последовательно, сначала 09.4.
- **Словарь кодов из 03 нужен перед контрактными тестами 02.** Существующие
  кирпичи валидации отвечают разными кодами (`INVALID_ID` vs

  раньше словаря, они закрепят коды, которые придётся менять — и правка станет
  «ломающей тесты», то есть отложится навсегда.
- **11 идёт перед 12.** Без измерения покрытия рефакторинг фронта идёт вслепую.
  Плюс `useSSE` из приоритетной пятёрки задачи 11 — предпосылка TDD-порядка
  задачи 12 (её главный риск про порядок инвалидации нечем зафиксировать).
- **08 не зависит от 05/06/07** и может идти параллельно им: пересечение только

## Открытые действия вне задач каталога

Это не рефакторинг и в оценки выше не входит. Перенесено из
`TECHNICAL_AUDIT_2026-07-19.md` при его удалении (задача 15.2) — там оно лежало
не закрытым и нигде больше не значилось.

- **Отозвать два токена Telegram через BotFather.** Аудит 2026-07-19 нашёл в
  служебных сценариях и документации два похожих на действующие токена. Из
  файлов значения убрали, сценарии теперь берут `BOT_TOKEN` из окружения и не
  печатают его — **но в истории git токены остались**, то есть считать их
  отозванными нельзя. Пока это не сделано, любой, у кого есть клон репозитория,
  имеет рабочий токен бота. Вычищение из истории (перезапись) — отдельная
  согласованная операция и **сама по себе проблему не решает**: токен уже
  утёк, и единственное, что его обесценивает, — отзыв.
- **Принятый риск:** три средние уязвимости в `@hono/node-server` (транзитивная,
  только через средство разработки Prisma). Исправление от npm понижает Prisma
  до 6 — не применять. Подробности в [15.2](15-repo-hygiene.md).
- **Две утечки между группами: сами дыры закрыты, причина — нет.** Админ своей
  группы читал историю правок чужой и статистику любого пользователя, потому
  что middleware проверял роль в группе, НАЗВАННОЙ В ЗАПРОСЕ, и не связывал её
  с ресурсом. Конкретные эндпоинты исправлены в `9829d5c8`; разбор — Находка 0
  в [матрице](04-auth-matrix.md). **План остатка — [04.1](04-1-group-scoping.md):**
  проверка факта эксплуатации (по текущим логам она невозможна — `userId` в них
  не пишется), починка логирования, снятие структурной причины с 8 оставшихся
  маршрутов.

## Правила исполнения

Взяты из `CLAUDE.md` и `AGENTS.md` проекта, повторены здесь, потому что при
рефакторинге их нарушают чаще всего:

1. **TDD там, где меняется логика.** Для переноса существующего кода —
   характеризующий тест **до** правки, фиксирующий поведение «как есть», а не
   «как должно быть». Тесты не меняются вместе с переносом: их неизменность и
   есть доказательство, что перенос ничего не сломал.
2. **Смотрите на порог `functions: 89`, не только на `statements: 94`.**
   `backend/jest.config.js` держит четыре порога. Extract-method плодит функции
   быстрее, чем строки, поэтому в задачах 05–08 первым красным станет
   `functions`. Понижать пороги нельзя — в комментарии к конфигу описано, чем
   закончилось прошлое понижение.
3. **Комментарии-обоснования переезжают вместе с кодом.** В этом репозитории
   комментарии несут историю решений (почему транзакция, почему барьер смотрит
   на `isSuccess`, почему один форк в Vitest). Потерять их дороже, чем потерять
   код — код восстанавливается, знание нет.
4. **Один коммит — одна причина.** Не смешивать перенос кода с изменением
   запросов, формата ответов или поведения. Иначе регрессию не отличить от
   рефакторинга, а `git bisect` бесполезен. Если разрез неизбежно тянет за
   собой правку всех импортёров (задача 07) — сначала переходный слой,
   потом перенос.
5. **Не заводить файлы-приставки.** `*.extensions.ts`, `*.helpers.ts`,
   `*-part2.ts` — признак того, что нарезка сделана по размеру, а не по домену.
   Если для куска кода не находится доменного имени, нарезка неверная.
6. **`knip` сейчас не доказывает отсутствие мёртвых экспортов.** В скрипте
   `--include files,dependencies,unlisted,unresolved,catalog,cycles` — **нет
   `exports`**, а в `knip.json` тестовые файлы в `entry` при
   `includeEntryExports: true`. Критерий «knip зелёный» осмысленен только после
   правки из задачи 09.1. Проверке `cycles` доверять можно.
7. **Документация — живой документ.** Не создавать `*_COMPLETE`, `*_SUMMARY`
   и снимки с датой; обновлять этот каталог по мере закрытия задач.
