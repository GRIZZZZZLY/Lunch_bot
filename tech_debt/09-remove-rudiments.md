## 9.1 Семь no-op шимов инициализации бота

`grep "@deprecated No-op: bot is now accessed"` → **7 вхождений**:

| Файл | Строка |
|---|---|
| `backend/src/services/budget.service.ts` | 16 |
| `backend/src/services/multi-category-responsible.service.ts` | 18 |
| `backend/src/services/order-calculation.service.ts` | 9 |
| `backend/src/services/recurring-poll.service.ts` | 44 |
| `backend/src/services/poll.service.ts` | 59 |
| `backend/src/services/poll.service.extensions.ts` | 17 |
| `backend/src/services/responsible.service.ts` | 13 |

Все имеют вид:

```ts
/** @deprecated No-op: bot is now accessed via the shared singleton */
export function initializePollServiceBot(_bot: unknown): void {}
```

Это остатки миграции на `bot/bot-instance.ts`. Пустая экспортируемая функция —
худший вид рудимента: она выглядит рабочей точкой расширения и её будут
вызывать. Заметьте, что `poll.service.ts` и `poll.service.extensions.ts`
экспортируют функцию **с одним и тем же именем** `initializePollServiceBot` —
кто из них попадёт в импорт, зависит от порядка импортов у вызывающего.

**Вызывающие — их меньше, чем кажется.** Продакшен-вызов ровно один:
`backend/src/index.ts:63` (`initializePollServiceBot(bot)`, импорт на строке 13,
из `./services/poll.service.extensions`). Остальные шесть шимов **не вызываются
вообще**. Плюс есть тест, который держит шим живым:
`backend/src/__tests__/unit/services/poll.service.extensions.test.ts:407` —
`expect(() => initializePollServiceBot({})).not.toThrow()` (импорт на строке 12).

**Почему `knip` это не поймал** (вопрос закрыт, доисследование не нужно):

1. В скрипте нет нужного включения —
   `knip --include files,dependencies,unlisted,unresolved,catalog,cycles`.
   **`exports` в списке отсутствует**, то есть knip в этом репозитории
   структурно не ищет неиспользуемые экспорты.
2. В `backend/knip.json` в `entry` перечислен `"src/**/*.test.ts"` при
   `"includeEntryExports": true` — значит импорт из теста удерживает
   продакшен-экспорт «живым» даже после добавления `exports`.

Отсюда следствие: **критерий «knip зелёный» ничего не доказывает** ни в этой,
ни в других задачах. Добавьте `exports` в `--include` — и тогда knip станет
инструментом, а не украшением. Пункт `"src/**/*.test.ts"` в `entry` при этом
придётся пересмотреть отдельно (он там, вероятно, чтобы knip не жаловался на
тестовые файлы как на недостижимые — есть более узкие способы это выразить).

**Что делать:** удалить вызов из `index.ts`, удалить тест на строке 407,
удалить семь экспортов.

**Перед удалением проверьте баррели.** Вывод «шесть шимов не вызываются» получен
grep'ом по имени функции, а реэкспорт звёздочкой (`export * from './budget.service'`
в каком-нибудь `services/index.ts`) таким grep'ом не ловится. Один
`grep -rn "export \*" backend/src` закрывает вопрос.

**Подводный камень:** удалять вызов, тест и объявления **одним** коммитом.
Если удалить объявление раньше вызова — сборка упадёт.

backend/src/services/vote.service.ts:768  // Получение голоса пользователя (DEPRECATED - используйте getUserVotes)

**Что делать:** проверить вызывающих (включая `bot/handlers/`, `poll.controller`,

## Что выяснилось при исполнении

### 9.4 оказался не «нулевым риском для поведения»

План писал: «только комментарии, нулевой риск». Из 28 испорченных строк
**девять — не комментарии, а строки для пользователя**: заголовки шаблонов
уведомлений и тела сообщений о старте голосования и напоминании о заказе.

Проверено, дошло ли это до людей: **нет, не дошло, но было в одном вызове от
этого.** `getTitle` не вызывается НИГДЕ ни для одного шаблона, а
`sendPollStartedNotification` и напоминание о заказе не имеют прод-вызывающих
(из шаблонного слоя в проде живут только `sendPollCompletionNotifications`,
`sendPollCancelledNotifications` и `notifyResponsible`, и они строят текст
сами). То есть порча лежала на неиспользуемых путях.

**Отдельная находка для задачи [07](07-notification-service-god-file.md):**
`getTitle` определён у каждого шаблона и не вызывается ни разу, а часть
`send*`-методов не имеет вызывающих. Значительная доля карты шаблонов —
мёртвый код, и это меняет объём разрезания.

Почему порча дожила до коммита: **ни один тест не смотрел на текст**. Все 77
тестов уведомлений проверяли, кому и сколько раз уходит сообщение, но не что
в нём написано. Добавлено 4 теста, закрепляющих читаемые строки; они сверяют
подстроки, а не шаблон целиком, чтобы не запрещать правку формулировок.

Техническая деталь, стоившая времени: наивная обратная перекодировка
`iconv.encode(текст, 'win1251')` даёт «Рнициализация» вместо
«Инициализация». Причина: в windows-1251 позиция **0x98 не определена**, а
UTF-8 «И» — это `D0 98`. Байт не пропал, он остался в файле управляющим
символом U+0098, и iconv подставляет на его месте `?`. Нужна обратная таблица
с тождеством `byte === codepoint` для 0x80..0x9F. Это записано в самом
скрипте проверки.

### 9.5 отклонён: `.design-sync/previews/` — входы инструмента, а не мёртвый код

План предлагал удалить 10 файлов «с мёртвыми экспортами», потому что их никто
не импортирует из `src`. Импортёров действительно нет — **и так задумано**:

- `.design-sync/config.json:12` перечисляет `./.design-sync/ds-theme-root.tsx`
  в `extraEntries`, а `provider.component` — `DSThemeRoot`. Удаление файла
  ломает конфигурацию инструмента.
- Девять `previews/*.tsx` — ровно по одному на каждый компонент из
  `componentSrcMap`. По документации инструмента
  (`frontend-new/.ds-sync/storybook/SKILL.md`) это **owned-переопределения**
  превью, которые сознательно перекрывают генерируемые.
- `NOTES.md:25` говорит прямо: «живёт вне src/ — приложение о нём не знает;
  это sync-only артефакт».

Файлы восстановлены. Вывод для остальных задач каталога: «нет импортёров в
`src`» не равно «мёртвый код», если каталог является входом внешнего
инструмента. Проверять надо конфигурацию инструмента, а не только граф
импортов.

### 9.6 закрыт реализацией

Уведомление автору предложения живёт в `MenuSuggestionService`, а не в
контроллере: это следствие домена, и любой другой вызывающий
approve/reject иначе его бы пропустил. Best-effort — решение уже записано,
недоставленное сообщение не превращает успешный запрос в ошибку.

**Ловушка, в которую я успел попасть и вылезти:** первый вариант добавлял
`telegramId: true` в `include.suggester.select` методов approve/reject. Их
результат уходит в ответ API — то есть Telegram-id автора начал бы отдаваться
наружу. Итоговый вариант берёт `telegramId` отдельным запросом
`prisma.user.findUnique`, а `select` в ответе остался прежним.
